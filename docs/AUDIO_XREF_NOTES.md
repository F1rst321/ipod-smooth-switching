# Аудиотракт: проверенные xrefs в OSOS 1.3

Эти наблюдения относятся к извлечённому `osos.bin` размером 7 561 216 байт,
SHA-256 `784ae3d5540fd2f89e8c947b93629e97f62a06dc311d9745aab143e4db6bb251`.
Адреса ниже — смещения от начала OSOS, а не адреса на диске. Бинарник и
резервные копии не менялись.

## `TPCMQUEUE`

- Строка `TPCMQUEUE` находится в `OSOS+0x240830`. Её адрес вычисляется
  инструкцией `ADD r1, pc, #0x1d8` в `+0x240650` внутри конструктора
  `+0x240614`; это не случайная строка без ссылки.
- В этом конструкторе поле `[object+0x10]` получает `0x400`, поле
  `[object+0x0c]` — указатель внутрь объекта (`object+0x658`). По одному
  числу `0x400` нельзя установить объём PCM в байтах или тип элемента.
- Единственный найденный прямой ARM `BL` к конструктору — `+0x25e298`.
  Вызов передаёт в `r0` статический адрес `0x149388b0`, в `r1` —
  `0x14939f60`. Значение `0x149388b0` встречается как буквальный адрес также
  в `+0x0feb08/+0x0feb18` и `+0x1b91b0`. Его наличие не измеряет свободную
  физическую память и не определяет отображение MMU.
- В той же инициализации `+0x25e2c0` вызывается `+0x24b5bc` с аргументом
  `0x40000`. Вложенный конструктор `+0x216b4c` именует эту структуру
  `FSbuf` (`+0x216c68`). Поэтому `0x40000` здесь относится к файловому
  буферу, а не доказанному запасу декодированного PCM.
- Объект `+0x24b5bc` хранит указатель на `TPCMQUEUE` в поле `+0x2e5c`.
  Его соседнее поле `+0x2e58` получает статический адрес `0x149e83a0`:
  инструкция `+0x25e2b4` передаёт адрес конструктору как `r2`, а
  `+0x24b6e0` сохраняет этот аргумент. Адрес `0x149e83a0` загружается в
  `+0x25dc50` для конструктора `+0x1f7fa8`, который инициализирует очередь
  и состояние сервиса. **Это не адрес самого I²S-объекта.** Отдельный
  конструктор I²S `+0x25de8c` получает `r0 = 0x149dd438 + 0x54 =
  0x149dd48c` (литерал `+0x25df48`) и `r1 = 0x70002800`. Связь сервиса
  `0x149e83a0` с аппаратным выходом требует отдельного трассинга.
  Поля двух объектов пока нельзя считать двумя потоками композиций.
  В `+0x249680` поле `+0x2e5c` передаётся в `+0x23f81c`, который создаёт
  сообщение с четырьмя 32-битными аргументами и ставит его в очередь через
  `+0x235250`. Просмотренный путь передаёт сообщение управления; в нём нет
  операции копирования сэмплов. Другие назначения этой очереди не исключены.

## Текущий объект потока из `TPCMQUEUE`

- Метод `+0x23f178` берёт указатель из `[TPCMQUEUE+0x78]`. В ветках
  `+0x24b1e8…+0x24b200` и `+0x24b268…+0x24b280` крупный объект проигрывателя
  сохраняет его в поле `+0x1950` и записывает указатель из своего поля
  `+0x2e58` в `[полученный объект+0x68]`. Это подтверждает связь текущего
  объекта с сервисом `0x149e83a0`, но не прямую связь с I²S и не тип
  аудиоданных.
- `[TPCMQUEUE+0x78]` задаётся в `+0x23fc24`: созданный объект имеет таблицу
  методов `OSOS+0x666284` (литерал в `+0x23fc48`). В него встроен объект
  `FSbuf`, сконструированный вызовом `+0x216b4c` в `+0x23fbec` и получающий
  таблицу методов `OSOS+0x674628` (литерал в `+0x23fc4c`). Таблицы содержат
  адреса методов как смещения от OSOS; нулевой метод основного объекта —
  `+0x125830`.
- Вызов через vtable в `+0x24944c` использует `[player+0x1950]`, поэтому
  направляется в `+0x125830`. Этот метод связывает поле объекта `+0x68`
  с `+0x1f7e88/+0x1f7ae4` и посылает сообщение через `TPCMQUEUE` в
  `+0x23f09c`. Метод `+0x125a0c` из той же таблицы задаёт длину блока,
  сравнивает её с `0x2000`, вызывает `FSbuf` и обновляет состояние очереди.
  Метод `+0x1258c4` читает вложенный `FSbuf` через его vtable и работает
  с буфером по `[объект+0x64ac]`. Это путь буферизации текущего потока;
  декодированные PCM-сэмплы в нём пока не распознаны.
- Показанное поле `TPCMQUEUE+0x78` содержит один указатель. Это **не**
  доказывает, что в других частях прошивки нет второго источника; но
  аргумента для одновременного декодирования A и B из этой ветки нет.
- Поле `player+0x1950` принимает также статические объекты
  `0x149e3780` и `0x149e37e4`: `+0x2492b0` кладёт их адреса в поля
  `+0x1968/+0x196c`, а `+0x24b0a0/+0x24b15c` выбирают один из них.
  Инициализация `+0x25d8c4` ставит этим объектам разные таблицы методов,
  `OSOS+0x668664` и `OSOS+0x666c80`. Разница их адресов `0x64` не является
  свидетельством двух музыкальных дорожек: обе альтернативы отличаются от
  создаваемого через `TPCMQUEUE` объекта с `FSbuf`.

## Строки статистики декодера

- `lost frames - decoder (failed to decode):` (`+0x1fa058`) адресуется
  из `+0x1f9cbc` и `+0x1f9eac`.
- `buffering transitions:` (`+0x1fa134`) адресуется из `+0x1f9d9c`.
- Оба обращения находятся внутри функции `+0x1f9b94`. Она вызывает
  `+0x1f9754`, который считывает поля статистики по именам, затем многократно
  форматирует значения из стековой структуры в текст. В частности,
  `+0x1f9d98` берёт значение из `[sp+0x4e4]` для строки
  `buffering transitions:`. Это счётчик диагностики буферизации, а не
  обнаруженный callback смены музыкального трека.
- Строка `fadeout` (`+0x26efe8`) используется сравнением имени команды в
  `+0x26efcc`; изученный фрагмент не декодирует и не смешивает PCM.

## Обработка блока в playback worker

Вызов `+0x23fc50` получает один блок от provider-а и передаёт его в
`+0x24ab48`. Проверка прямых ссылок в Ghidra показывает, что `+0x24ab48`
вызывается только из этого worker-а. Внутри `+0x24ab48` интерфейс
`player+0x909c` получает один и тот же указатель как источник и назначение.
При включённых ветках дополнительно вызываются `+0x2403c4` и
`+0x20dd78`; последняя функция также получает один и тот же буфер как вход
и выход. `+0x249bc4` расширяет 8-битные данные в 16-битные на месте.

`+0x20dd78` содержит обработку сохранённого состояния и интерполяцию сэмплов,
но её единственный найденный caller — `+0x24ab48`, и этот вызов не передаёт
второй PCM-указатель. Поэтому это кандидат на обработку одного текущего
буфера, а не подтверждённый микшер двух композиций. Связь этого блока с
выходной очередью I²S всё ещё не установлена. Результат воспроизводится
read-only разбором функций `0x23fc50`, `0x24ab48`, `0x2403c4`, `0x249bc4`,
`0x20dd78` и их xref-ов в локальном Ghidra-проекте; лог
`build/ghidra-audio-render-trace2.log` не входит в Git.

## Выходной callback и неизвестный producer

`+0x25a614` находится в таблице методов I²S-объекта. Конструктор
`+0x18c85c` сохраняет аппаратную базу `0x70002800` и адреса `base+0x40` /
`base+0x80`; вызванный при инициализации `+0x18c6d8` создаёт для них
объекты через `+0x1a3080` и `+0x1a2790`. Для первого таблица методов
начинается с `+0x66d308`, где слот `+0x08` указывает на `+0x1a2b74`.
Этот метод выделяет рабочие 256 KiB, запрашивает у общего менеджера
`+0x1254d0` интерфейс с числовым типом `1` и передаёт блоки в
`+0x1a2d60`; типичный размер блока — `0x2400` байт. Связь `+0x25a614`
с тем же I²S-объектом подтверждается таблицей `+0x66d338`.

Вызов `+0x1e0d60` доказанно относится к объекту `SpdifEbuScanner`: его
конструктор `+0x18d5fc` сохраняет имя в поле объекта, а таблица
`+0x66c154` помещает worker `+0x18d3b4` в слот `+0x0c`; этот worker вызывает
`+0x1e0d60`. Внутри `+0x1e0d60` запрашивается интерфейс типа `1` и обрабатываются
записи кольцевого буфера по `0x1e4` байта (16 слотов, до `0x1e0` байт полезных
данных в слоте). Это отдельный S/PDIF scanner путь, а не доказанный музыкальный
декодер.

Тип `1` также запрашивается в `+0x1a2b74` на ветке I²S-выхода и встречается в
`+0x1d9f3c`. Общий диспетчер `+0x1254d0` принимает контекст запроса, поэтому
совпадение числового ID не доказывает, что все вызовы возвращают один и тот же
источник PCM. Следующий анализ должен установить конкретный объект и формат
данных, возвращаемые именно для ветки `+0x1a2b74`, и связать их с музыкальным
декодером.

### Отдельная пара указатель/длина в I²S-очереди

Повторная трассировка очереди, которую опрашивает `+0x1a2b74`, уточнила её
назначение. `+0x132c8c` кладёт пару `(pointer, length)` в кольцо объекта, а
`+0x1a2b74` вынимает такую пару и передаёт её в `+0x1a2d60`; если кольцо пусто,
передаётся участок временного буфера длиной `0x2400`. Это отдельная
буферная очередь, не очередь сообщений `TPCMQUEUE` из предыдущего раздела.

Найдены реализации поставщиков `+0x1b8100` и `+0x1b8178`: обе проверяют
состояние объекта и ставят полученные указатель и длину в две разные очереди,
сохранённые в полях `+0x20` и `+0x24`. Их владелец теперь связан с
инициализацией I²S: `+0x25de8c` вызывает `+0x1b81d4` для объекта в
`[I2S object+0x360]`; `+0x1b81d4` записывает в его первый слот таблицу
`OSOS+0x66e1b0`, где находятся обе функции-поставщика. Инициализатор
`+0x1b7fdc` создаёт связанные буферные узлы через `+0x1a3080` и `+0x1a2790`.
Это связывает две очереди с I²S-объектом и подтверждает асинхронную подачу
блоков в выходной тракт. Но оно не показывает, что содержимое — музыкальный
PCM, и не означает, что две очереди принадлежат двум композициям. Музыкальный
producer, формат буферов, их связь с `+0x1a2b74` и безопасная точка
суммирования всё ещё не установлены.

Проверено в Ghidra по OSOS с SHA-256, указанным выше; использованы
`DumpRetailFunctions.java` для смещений `0x132c8c`, `0x1a2b74`, `0x1a2d60`,
`0x1b7fdc`, `0x1b8100`, `0x1b8178`, `0x1b81d4`, `0x25de8c`, `0x18c82c` и
чтение таблицы методов у `OSOS+0x66e1b0`. Записи исследования находятся в локальных логах
`build/ghidra-pcmqueue-writer-trace.log`,
`build/ghidra-audio-helper-trace.log`, `build/ghidra-queue-producers.log` и
`build/ghidra-player-codec-class.log`, `build/ghidra-audio-init-link.log` и
`build/ghidra-audio-object-registration.log`; каталог `build/` не публикуется.
Полный автоматический анализ Ghidra (70 секунд на точном OSOS) не добавил
статических xref-ов на слова таблицы по `+0x66e1b0…+0x66e1d4`; связь таблицы
с I²S при этом подтверждается явным вызовом конструктора `+0x1b81d4` из
`+0x25de8c`, а её связь с музыкальным playback-context остаётся открытой.

### Объект, выдаваемый интерфейсом типа `1`

Связь запроса из callback с активным выходным классом уточнена по HIBE. В
снимке указатель singleton-а `0x1081ecc8` ведёт на менеджер в RAM
`0x1086cc18`; его таблица `0x670284` хранит в слоте `+0x28` метод
`+0x1d98d0`. Декомпиляция этого метода показывает, что запрос с типом `1`
выбирает очередь по `[manager+0x44]` и извлекает из неё объект, когда очередь
помечена активной. В сохранённом состоянии очередь активна, содержит три
указателя, и все три указывают на объекты с таблицей `OSOS+0x66d528`.
Callback `+0x1a2b74` запрашивает как раз тип `1`, поэтому это связывает его
путь с объектами данного выходного интерфейса; конкретный выданный экземпляр
зависит от состояния очереди.

`+0x1a2d60` в состоянии объекта `0xd`/`0xf` вызывает его виртуальный метод
`+0x40`, адрес которого в таблице `+0x66d528` равен `+0x28ea7c`. Эта функция
сохраняет входные адреса и длину в структуре задания. Другой метод этого
класса, `+0x28ea14`, записывает указатели и длину в регистровую структуру;
прямая связь между этими двумя методами ещё не подтверждена. Это кандидат на
передачу буфера аппаратному аудиотракту и наиболее конкретное
место для дальнейшей проверки смешивания. При этом статический/HIBE-разбор
не определяет формат данных и не доказывает, что переданный блок — PCM
музыкального декодера. Второго музыкального потока в очереди или в снимке
не обнаружено.

Дополнительная проверка таблицы методов `+0x66d528` и базового обработчика
задания уточнила связь этих методов. `+0x28ea7c` находится в слоте `+0x40`;
после постановки задания обработчик `+0x124c44` вызывает виртуальный метод
слота `+0x58`, который для этого класса разрешается в `+0x28ea14`. В свою
очередь, `+0x28ea14` пишет сохранённые адреса буфера и длину в поля регистровой
структуры. Поэтому связь постановки блока и последующей настройки I²S DMA
подтверждена через виртуальную диспетчеризацию, а не прямым вызовом. Это
фиксирует выходную границу буфера; producer PCM и второй музыкальный поток
остаются неустановленными.

Runtime-инстанс callback `OSOS+0x66d308` найден в HIBE по RAM `0x1086ea10`;
его поле `+4` указывает на endpoint-объект `0x1086c814` с vtable
`OSOS+0x66d528`. В endpoint сохранены назначение `0x70002840`, адрес буфера
`0x14a66560`, второй адрес буферного слота `0x14a68960` и длина текущего блока
`0x2400` байт. Адреса разделены ровно на `0x2400`, что согласуется с двумя
смежными выходными блоками; это не указывает на два декодированных трека.
Оба адреса находятся вне диапазона 32 MiB, включённого в HIBE, поэтому
содержимое буферов по снимку проверить нельзя. Read-only скрипт печатает оба
адреса, длину и расстояние между слотами.

HIBE-наблюдения воспроизводит read-only скрипт
`tools/inspect_hibe_audio.py`; он проверяет копию OSOS в RAM-снимке, читает
только локальный backup и печатает адреса и vtable offsets, не содержимое
аудиобуферов.

В конструкторе playback-объекта `+0x24b5bc` сохраняются результаты selectors
`FUN_10111c58` (`+0x111c58`) и `FUN_10112ee0` (`+0x112ee0`).
`FUN_10111c58` выбирает один из трёх внешних
endpoint-адресов (`0x149dd4c8`, `0x149dd554`, `0x149dd638`) по selector-у
`+0x2653a4`, который возвращает значения 1–3 для распознанных состояний.
Значения endpoint-ов расположены за пределами файла OSOS; в извлечённом образе
видны только адресные константы, не структуры объектов. Это связывает объект
плеера с выбором аппаратного аудиовыхода, но не показывает, где в endpoint
поступают PCM-блоки. Объект `FUN_10112ee0` возвращает ещё один внешний адрес
`0x149dd750`; его назначение пока также не определено.

Не найдены: подтверждённый producer PCM музыки; формат сэмплов на этом
интерфейсе; момент предварительной загрузки следующей композиции; второй
одновременно декодированный поток; свободная память для хвоста текущего
трека; безопасный hook для микшера. Само имя `TPCMQUEUE` и диагностическое
слово `transitions` не заполняют эти пробелы.

### Входной блок потока в playback worker

Разбор worker-а `+0x285b70` подтвердил, что для активного сообщения из
очереди он вызывает `+0x249390(player, item)`. В `+0x249390` выполняются
виртуальные операции над `item` в слотах `+0x08`, `+0x14`, `+0x18` и
`+0x34`; при успешном состоянии worker получает буфер у объекта
`player+0x1950` через слот `+0x10` и передаёт указатель в слот `+0x18` item.
Класс объекта `player+0x1950` в переходном режиме — `OSOS+0x666284`; его слот
`+0x10` указывает на `+0x1258c4`, который читает вложенный `FSbuf` в буфер
объекта. Это подтверждает передачу текущих потоковых данных item-у, а не PCM
на I²S. Слот item `+0x18` может участвовать в обработке/декодировании, но без
определения его класса это не доказательство конкретного кодека или PCM
выхода.

Переходные состояния в обработчике `+0x24addc` для некоторых режимов получают
объект через `+0x23f178(TPCMQUEUE, &object)`. Эта функция просто возвращает
`TPCMQUEUE+0x78`, если поле ненулевое. Затем код сохраняет в объекте `+0x68`
указатель из `player+0x2e58` и помещает объект в `player+0x1950`. В
инициализации `+0x25e2b4` поле `+0x2e58` получает статический адрес
`0x149e83a0`, связанный с очередью/сервисом потока; это не установленный
PCM-output wrapper. Вызов `+0x23f09c` копирует блок параметров в
`TPCMQUEUE+0x80`; он не смешивает PCM.

Пока не доказано, что эти методы могут создать второй decoder/item для
следующей композиции или запросить её данные до завершения текущего трека.
Обнаружен путь буферизованных данных текущего потока до item-а; место PCM
выхода и безопасный mixer hook остаются неизвестными.

### Другие режимы `player+0x1950`

`player+0x1950` — интерфейс с разными классами в зависимости от состояния,
поэтому вывод о `FSbuf` выше относится только к режиму, где объект берётся из
`TPCMQUEUE+0x78`. В двух соседних режимах поле выбирает статические объекты
`0x149e3780` и `0x149e37e4`, чьи vtable равны `+0x668664` и `+0x666c80`.
У обеих таблиц слот `+0x10` указывает на `+0x163dc8`; этот метод запрашивает
буфер у внешнего интерфейса через `EXT_FUN_4001da34` и вызывает
`+0x1a88dc` для преобразования данных в соответствии с параметрами объекта.
Слот `+0x18` указывает на `+0x163eec` и сохраняет указатель буфера в
`object+0x10`. После получения блока worker может вызывать `+0x163ebc` и
`+0x163e88`, которые выполняют измерения уровня/пиков для текущего буфера.

Это показывает отдельный audio-buffer интерфейс помимо `FSbuf`-пути. В коде
`+0x1a88dc`, `+0x163ebc` и `+0x163e88` не обнаружено сложения двух сигналов;
`EXT_FUN_4001da34` и связь этих буферов с I²S callback ещё не разрешены.
Нельзя пока считать этот интерфейс подтверждённым PCM mixer hook.

#### Как выбирается один из двух wrapper-ов

Декомпиляция `+0x24addc` уточнила назначение полей `player+0x1968/+0x196c`.
Конструктор `+0x24b5bc` заполняет `player+4` результатом селектора `+0x111c58`,
а `player+8` — результатом `+0x112ee0`. Первый селектор возвращает один из
внешних endpoint-указателей `0x149dd4c8/0x149dd554/0x149dd638` в зависимости
от результата `+0x2653a4`; второй возвращает внешний адрес `0x149dd750`.
Следовательно, эти поля являются выбранными runtime endpoint-ами, а не
доказанными контекстами декодирования следующего трека.

В событиях `0x0d` и `0x0e` обработчик по разным веткам присваивает endpoint
из `player+4` либо `player+8` полю `+0x2c` соответствующего статического
wrapper-а, а затем записывает только его адрес в `player+0x1950`. В обеих
ветках обновляются общие поля формата; в рамках события второй wrapper не
вызывается. Значение событий `0x0d/0x0e` этим не установлено.

`+0x285b70` назначает в `player+0x1968` адрес `0x149e37e4`, а в
`player+0x196c` — соседний объект `0x149e3780`. Инициализатор `+0x25d8c4`
связывает их с таблицами `+0x666c80` и `+0x668664`; последние указывают на
разные конструкторы `+0x138e28` и `+0x143a10`. Оба конструктора используют
общий `+0x163d04`, но вызывают `+0x23f294` с разными режимами 2 и 1.

В playback-worker `+0x249390` через выбранный `player+0x1950` запрашиваются
состояние, один блок через слот `+0x10` и его завершение через слот `+0x18`.
Getter `+0x163dc8` получает ровно один указатель блока от
`EXT_FUN_4001da34` и передаёт один и тот же адрес как источник и назначение
`+0x1a88dc`. Это подтверждает переключение между двумя конфигурациями одного
буферного пути; оно не доказывает два decoder-а или одновременные потоки A/B.
Сами статические wrapper-ы и их внутренние преобразователи не являются
подтверждённой точкой кроссфейда.

Рядом с этим путём обнаружена отдельная обработка голосовых звуков. В
`+0x23f8dc` из записи менеджера с ключом `0x18` создаются небольшие объекты
обёртки через `+0x1d60a4` в режимах 1 и 2. Их таблица `+0x67006c` содержит
callback `+0x1d603c`; при нулевом младшем байте флага он вызывает
`+0x10217cb8` для одного буфера и числа 16-битных кадров. `+0x10217cb8`
применяет коэффициент громкости к этому буферу и обходит четыре объекта
голосового пула (`+0x10146ba4`). Это подтверждает mixer-подобную обработку
буфера звуковых эффектов/голосов, но не добавляет второй источник музыкального
PCM и пока не связывает данные callback-а с PCM декодера или I²S DMA. Его нельзя
использовать как доказанный кроссфейд-хук.

Уточнение по data path: сам `+0x217cb8` получает один выходной блок, но это
не означает, что renderer одноисточниковый. `+0x146ba4` для каждого активного
voice-слота берёт его отдельный PCM-указатель из `voice+0x1c` и вызывает
форматный renderer с source и текущим destination. В таблице по
image-relative адресу `OSOS+0x2a9a24` есть renderer `+0x146624` для PCM16
stereo без ресэмплирования; он складывает каждый voice-сэмпл с уже имеющимся
выходным сэмплом и ограничивает сумму диапазоном int16. Поэтому в playback
callback подтверждён настоящий post-decode voice PCM mixer: основной PCM-блок
плюс отдельные PCM voice-сэмплы. Не подтверждено, что voice descriptor может
получить поток второй музыкальной дорожки или что его PCM producer существует.
Renderer — кандидат для подачи уже декодированного B, но decoder/producer B
остаётся не найден.

#### Runtime-образ внешнего buffer helper

16 октября 2026 года в отдельном запуске 5.5G-эмулятора `warm` сохранён регион
IRAM размером `0x20000` байт. В диапазоне IRAM `+0x1d800..+0x1faf4`
(`0x22f4` байта) он побайтно совпадает с OSOS `+0x7335cc..+0x7358c0`;
остальные совпадающие отрезки продолжаются до конца сохранённого региона.
В частности, код IRAM `0x4001da34` совпадает с OSOS `+0x733800`, на который
указывает veneer `OSOS+0x844ec`. Это объясняет, почему простой анализ файла
показывал только адрес вне OSOS, хотя тело helper-а присутствует в том же
образе прошивки.

Декомпиляция восстановленного тела показывает, что helper обнуляет выходной
указатель, читает флаг объекта `+0x65` и интерфейс из `+0x5c`, а затем вызывает
один из методов интерфейса для получения элемента. При типе `1` veneer
`OSOS+0x7327a0` переходит к `+0x1c6e88`: тот выбирает запись из кольца до семи
элементов с шагом `0x1c` байт и возвращает адрес записи после успешного
заполнения. Единственный прямой ARM-вызов veneer `+0x844ec` в OSOS найден в
`+0x163dc8`; метод затем передаёт полученный указатель и параметры объекта в
`+0x1a88dc` для преобразования данных на месте.

Это уточняет форму buffer-provider API, но не устанавливает тип содержимого
его записей, принадлежность музыкальному декодеру, связь с очередью I²S или
возможность одновременно получить данные следующего трека. Тело было
сопоставлено статически с runtime IRAM-снимком; эмуляторная сессия не дошла до
музыкального воспроизведения. Следовательно, это всё ещё не доказанная точка
PCM-микширования.

#### Остальные provider-вызовы playback-потока

Сопоставление 64-байтовых участков runtime IRAM с точным OSOS разрешило ещё
несколько ранее внешних вызовов. `EXT_FUN_4001d644` и `EXT_FUN_4001d660`
переходят к `OSOS+0x733410` и `+0x73342c` (вызов методов provider-а через
vtable `+4` и `+0xc`); `EXT_FUN_4001d67c` — к `+0x733448`, который перебирает
таблицу provider-ов и вызывает слот `+0`. `EXT_FUN_4001d6d0` — к `+0x73349c`:
он так же перебирает список, но вызывает слот `+8` с запрошенным типом и
возвращает индекс первого совпавшего provider-а. `+0x7334f0` возвращает
сохранённый индекс, а `+0x733518/+0x733534` проверяют состояние provider-а
`+8` на значения 1 и 2. `+0x733550` назначает provider-ам индексы и запоминает
первый в состоянии 1; `+0x73363c` добавляет объект в глобальный список,
ограниченный восемью элементами.

Это registry нескольких **provider-объектов**, а не список доказанных
декодеров. В обработчике playback-событий `0x0d/0x0e` вызов `4001d6d0`
проверяет выбранный provider, после чего код устанавливает один соответствующий
wrapper в `player+0x1950`. В пределах каждой ветки второй wrapper и второй
PCM-указатель не используются. Регистрация нескольких provider-ов поэтому не
доказывает одновременную работу двух музыкальных потоков.

`EXT_FUN_400189f4` из worker-а `TPCMQUEUE` сопоставлен с `+0x722b20`: он
запрашивает один элемент у интерфейса `[task+0x5c]` и читает из descriptor-а
поле `+0x00` (адрес блока) и поле `+0x08` (смысл пока не установлен); цикл worker-а затем проводит тот же блок через
`+0x24ab48` и форматирующий вызов `+0x1a88dc` с одинаковыми указателями
источника и назначения. `EXT_FUN_40018ab0` и `40018b0c` соответствуют
`+0x722bdc/+0x722c38` — обработчикам состояния/событий этого playback-контекста.
`EXT_FUN_4001dd28` соответствует `+0x733af4` и обновляет позицию/счётчик
воспроизведения; это не аудиоданные. Эти сопоставления уточняют один путь
обработки текущего источника, но не дают второго декодера или hook-а суммирования
двух композиций.

Повторить сопоставление можно локальным read-only скриптом (снимок IRAM
создаётся внешним эмулятором и не публикуется в Git):

```powershell
py tools/map_iram_aliases.py firmware/extracted/audio-analysis/osos.bin `
  build/audio-analysis/iram-after-600m.bin --window 64 `
  0x400189f4 0x40018ab0 0x40018b0c 0x4001d644 0x4001d660 `
  0x4001d67c 0x4001d6d0 0x4001d724 0x4001d74c 0x4001d768 `
  0x4001d784 0x4001d870 0x4001da34 0x4001dd28
```

Воспроизвести сравнение можно после извлечения точного OSOS и запуска
`ipod-boot warm` из внешнего 5.5G-эмулятора с `--save-region=iram:<файл>`.
Проверенная локальная IRAM-копия хранится в игнорируемом каталоге
`build/audio-analysis/iram-after-600m.bin` и в Git не добавляется.

#### Image-relative vtable entries

При проверке почему Ghidra не показывал ссылки на эти методы выяснилось, что
слова в OSOS-файле хранят адреса кода как смещения от начала образа. Например,
в таблицах по `+0x668664` и `+0x666c80` лежат слова `0x00163dc8` и
`0x00163eec`, а не загруженные в RAM адреса `0x10163dc8` и `0x10163eec`.
Третья таблица по `+0x669eac` также содержит методы `+0x163dc8`, `+0x163e08`
и `+0x163eec`. Объекты в `+0x149e3780` и `+0x149e37e4` получают первые две
таблицы при инициализации `+0x25d8c4`.

Это объясняет, почему поиск только абсолютных указателей и обычные Ghidra
xrefs пропускали эти виртуальные методы. `tools/find_pointer_references.py`
теперь показывает и image-relative, и абсолютные aligned-указатели. Это
исправляет поиск ссылок в таблицах, но само по себе не разрешает внешний
`EXT_FUN_4001da34`, не доказывает содержимое получаемого буфера и не связывает
его с очередью I²S.

### Размер блока и параметры звука

Инициализатор `+0x24b458` задаёт начальные поля `player+0x2e28 = 2` и
`player+0x2e29 = 16`. В `+0x24a024` размер блока вычисляется с множителями
числа каналов, ширины сэмпла в байтах и `0x480` кадров. При этих начальных
значениях размер равен `2 × (16 / 8) × 0x480 = 0x1200` байт. Это
подтверждает начальную конфигурацию с двумя каналами и 16-битной шириной
сэмпла; в рабочем пути значения могут меняться по метаданным item. Знаковость
PCM, порядок каналов и формат для каждого кодека из этого расчёта не следуют.

Размер `0x2400` из HIBE ровно вдвое больше рассчитанного начального блока
`0x1200`, но связь между этими адресными областями и двумя блоками worker-а
пока не доказана. Это арифметическое совпадение помогает задать эксперимент,
но не подтверждает формат DMA-слотов или содержимое буферов.

## Вариант с одним декодером

Сохранение хвоста A и последующее декодирование начала B потребовало бы при
44 100 Гц, двух каналах и PCM16 ровно 1 764 000 байт для 10 секунд
(`44 100 × 2 × 2 × 10`) или 529 200 байт для 3 секунд. Эти числа — расчёт
по предполагаемому формату, не измерение штатного буфера. Ещё требуются
подтверждённый сигнал переключения декодера до конца A, доступная память,
корректная передача метаданных и обработка паузы/перемотки. Пока данных для
такого патча нет.

## Worker аудиоочереди `TPCMQUEUE`

Дополнительно разобран объект `TPCMQUEUE` и его worker в точном OSOS. Конструктор
`+0x240614` записывает имя `TPCMQUEUE` и таблицу методов `+0x67782c`; этот
объект создаётся при инициализации playback-контекста из `+0x25e298`. В таблице
методов слот `+0x0c` содержит image-relative указатель на `+0x23fc50` — цикл,
который сначала требует успешного создания четырёх записей/голосов через
`+0x23f8dc`, затем ждёт блоки и обрабатывает их.

Вызов `EXT_FUN_400189f4` сопоставлен с кодом `OSOS+0x722b20`: все 104 байта
IRAM `+0x189f4` совпадают с этим смещением в OSOS. Helper обращается к
интерфейсу `[task+0x5c]`, получает из descriptor-а указатель блока и ещё одно
поле `+0x08` с пока неустановленной семантикой,
после чего worker передаёт этот блок в `+0x24ab48`, применяет преобразование
формата через `+0x1a88dc` и продолжает обработку. В статическом OSOS три
`BL` внутри `+0x722b20` кажутся вызовами `+0x727018`, `+0x726b84` и
`+0x726b20`. Однако после копирования в IRAM адреса целей содержат **другие**
функции: `+0x732cb8` (получение descriptor-а), `+0x732824` (чтение одного поля)
и `+0x7327c0` (чтение другого поля). Следовательно, прежняя интерпретация
`+0x726b84/+0x726b20` как выполняемых здесь арифметических функций неверна:
этот helper не смешивает два массива. `+0x24ab48`
получает один указатель блока за вызов, и его единственный найденный прямой
caller — этот worker.

Это первый прослеженный worker, связанный одновременно с playback-объектом и
обработкой аудиоблоков, поэтому `TPCMQUEUE`/`+0x24ab48` — лучший из найденных
кандидатов для дальнейшего исследования. Связь блока с выходным callback I²S
`+0x1a2b74` и возможность заранее получить PCM следующей песни всё ещё не
доказаны. Код кроссфейда пока нельзя безопасно вставить или проверить.

#### Descriptor-ы PCM provider-а в HIBE-снимке

Объект `TPCMQUEUE+0x5c` указывает на uncached-адрес `0x1486c6a0`, то есть на
native RAM `0x1086c6a0`. Его таблица по `+0x30` начинается в RAM `0x1086c310`
и имеет ёмкость 32 descriptor-а (`+0x34`). В HIBE заполнены первые 16:
каждый указывает на данные, имеет длину `0x1200` байт и состояние 3; адреса
данных идут с шагом `0x4000`. Все 16 блоков содержат ненулевые данные. SHA-256
их конкатенации по порядку —
`a07a5af06f6a8c8319707935d78d4eb2dcba9e577b4dec8b5c94f9eab276520b`.
Интерпретация как little-endian int16 даёт диапазон значений -12527…14540.

Размер `0x1200` точно совпадает с размером блока, рассчитанным playback path
для 2 каналов, 16 бит и 1152 кадров. Worker `+0x23fc50` запрашивает данные
provider-а через `+0x722b20`, передаёт блок через `+0x24ab48`, а затем
обрабатывает его in-place функцией `+0x1a88dc`. Совпадение формата и длины,
ненулевое содержимое descriptor-ов и связь с worker-ом — сильное свидетельство
PCM-подобных блоков текущего playback-контекста. Но HIBE сам по себе не
идентифицирует upstream decoder и не подтверждает реальный output этих блоков
на I²S. Он показывает один TPCMQUEUE/file wrapper и один provider; второго
producer-а или композиции B не видно. Вывод воспроизводит
`tools/inspect_hibe_audio.py` без доступа к устройству.

Runtime-снимок связывает этот worker с task-объектом `RMIprimary`: RAM
`0x1093733c`, vtable `OSOS+0x666348`; его поле `+0x4c` указывает на тот же
`TPCMQUEUE` по uncached-адресу `0x149388b0`. Статический метод `+0x25e148`
создаёт task с именем `RMIprimary` и вызывает конструктор `TPCMQUEUE`
`+0x240614`. В этом HIBE capture обнаружен один экземпляр обоих объектов и
один `TPCMQUEUE+0x78` playback/file wrapper. Это связывает PCM-подобные
descriptor-ы с активным основным playback context, но не доказывает, что код
RetailOS принципиально не способен создать ещё один контекст в другом состоянии.

#### Коррекция прямых вызовов в IRAM

Код RetailOS копируется в IRAM не одним непрерывным куском OSOS. Для
`EXT_FUN_400189f4` исходные 104 байта точно соответствуют `OSOS+0x722b20`,
но его относительные `BL` исполняются по адресам IRAM, где находятся другие
копии OSOS. Проверка сохранённого IRAM по 32-байтовым уникальным окнам дала:

| Смещение BL | Цель в IRAM | Фактический OSOS | Наивная цель в файле |
| --- | --- | --- | --- |
| `+0x38` | `0x4001ceec` | `+0x732cb8` | `+0x727018` |
| `+0x50` | `0x4001ca58` | `+0x732824` | `+0x726b84` |
| `+0x5c` | `0x4001c9f4` | `+0x7327c0` | `+0x726b20` |

`+0x732cb8` выбирает descriptor через таблицу provider-а, а две следующие
функции читают его поля `+0x08` и `+0x00`. В сохранённом HIBE у заполненных
descriptor-ов поле `+0x04` равно `0x1200`, а `+0x08` равно нулю; поэтому
`+0x08` нельзя называть длиной на основании этого снимка. Статическая
декомпиляция `+0x722b20` в Ghidra
показывает правильную форму вызова, но **неправильные тела вызываемых функций**
без этой runtime-переадресации. Исследовательский скрипт
`tools/trace_iram_calls.py` воспроизводит сопоставление из точного OSOS и
локального IRAM-снимка; отсутствие уникального совпадения он считает ошибкой.

Таблица provider-а имеет ёмкость 32 descriptor-а по `0x1200` байт. Даже если
все они заполнены stereo PCM16 при 44,1 кГц, это только 36 864 кадра, то есть
примерно 0,836 секунды. Для требуемого перекрытия 3–10 секунд текущей ёмкости
недостаточно; варианту с одним декодером нужна отдельная проверенная память
для удержания ещё не прозвучавшего хвоста A.

```powershell
py tools/trace_iram_calls.py firmware/extracted/audio-analysis/osos.bin `
  build/audio-analysis/iram-after-600m.bin 0x400189f4 --length 0x68
```

В HIBE поле `TPCMQUEUE+0x68` указывает на отдельный объект с vtable
`OSOS+0x67006c`; его слот `+4` ведёт к `+0x1d603c`, который вызывает
`+0x217cb8` для наложения системных голосов на текущий PCM-блок. Поле
`TPCMQUEUE+0x5c` указывает на буферный provider `0x1086c6a0`. Это два
различных объекта. Сохранённый снимок содержит две ссылки на provider
(`TPCMQUEUE+0x5c` и объект по `0x1086c2e0+0x0c`), но не обнаруживает
производителя PCM следующей композиции.

## Воспроизведение поиска

```powershell
py tools/find_arm_pc_xrefs.py firmware/extracted/audio-analysis/osos.bin --target 0x240830
py tools/find_arm_pc_xrefs.py firmware/extracted/audio-analysis/osos.bin --target 0x1fa134
py tools/find_arm_callers.py firmware/extracted/audio-analysis/osos.bin --raw-osos --target 0x240614
```

Поиск xrefs синтаксический: каждое совпадение нужно проверять контекстом
дизассемблирования, потому что данные могут походить на инструкции ARM.
