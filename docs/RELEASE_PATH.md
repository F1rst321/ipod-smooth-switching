# Проверка и выпуск патча RetailOS 1.3

Дата проверки источников: 16 октября 2026 года. Цель — штатная прошивка iPod Video 5.5G 30 GB (`iPod_25.1.3.ipsw`, семейство обновления 25), без загрузчика и системы Rockbox. Этот документ — последовательность проверок для будущего **реально реализованного** патча. Структурный образ, собранный из случайно изменённого OSOS, ей не соответствует.

## Что можно проверить до записи

| Проверка | Сейчас доступна | Что доказывает |
| --- | --- | --- |
| Точный SHA-256 обеих оригинальных копий | Да | Резерв для возврата не изменён |
| Побайтовая обратная сборка из штатных OSOS/RSRC | Да | Смещения, длины и суммы контейнера поняты для этой копии |
| Сборка изменённых компонентов прежнего размера и `verify` | После реализации компонентов | В образе изменены только OSOS/RSRC и их поля сумм |
| Запуск UI в эмуляторе iPod Video | Может потребовать адаптации для 5.5G | Меню рисуется и реагирует на колесо в условиях эмуляции |
| Звук, перекрытие двух декодированных треков и переходы | Только на реальном устройстве | Требуемый эффект действительно работает |

Оригинальные `firmware/ipod_video_5.5g_30gb_stock_partition1.img` и `D:\ipod_video_5.5g_30gb_stock_partition1.img` должны иметь **98 574 336 байт** и SHA-256 `010bda520671d86a5a2cb010b57ee4484c980e54d97eb3e12621e08cde0423a3`. Перед любыми работами сверять обе копии повторно. Сборщик `tools/build_partition_image.py` допускает только исходный SHA и создаёт новый файл в `build/`; его `preflight` не пишет образ. Подробности — [IMAGE_FORMAT.md](IMAGE_FORMAT.md).

## Эмуляторы

[ipod-emulator](https://github.com/siggifly/ipod-emulator) запускает RetailOS с меню и колесом, принимает собственную IPSW или образ диска и предоставляет `ipod-boot make-disk`. Но его опубликованная проверенная пара — реальный ROM 5G с `iPod_20.1.3.ipsw`; наши 5.5G и `iPod_25.1.3.ipsw` **не заявлены как проверенная пара** ([описание проверенных файлов](https://github.com/siggifly/ipod-emulator/blob/dev/docs/GETTING-THE-FILES.md), [план поддержки 5.5G](https://github.com/siggifly/ipod-emulator/blob/dev/ROADMAP.md)). В модели нет выхода звука: WM8758, I²S и DMA не реализованы ([README](https://github.com/siggifly/ipod-emulator)). Если адаптировать образ и он загрузится, это может проверить только отображение и управление. Отказ загрузки здесь сам по себе не означает неисправность патча.

[qemu-ipod-classic](https://github.com/davidmonterocrespo24/qemu-ipod-classic/blob/main/README.md) умеет меню iPod Video 5G, но для этой модели не моделирует I²S/WM8758; VideoCore не исполняется. Аудио iPod Classic 6G в том же проекте относится к другому SoC и не подтверждает 5.5G. Его скрипты `navtest.sh`/`appletest.sh` сами не являются утверждающими тестами. Следовательно, **эмуляторного доказательства кроссфейда сейчас нет**.

## Критерии функциональной проверки

После получения настоящих OSOS/RSRC-патчей и прохождения офлайн-проверки на устройстве нужны наблюдаемые результаты:

1. Штатная RetailOS загружается; существующие меню, воспроизведение и колесо работают.
2. В «Настройки» есть «Плавный переход». Прямой ползунок с круглым бегунком меняет значения **3–10 секунд** по колесу; число читается, не перекрывает соседние элементы, выбранное значение сохраняется после перезагрузки.
3. Два последовательно проигрываемых трека разного звучания **одновременно слышны** в переходе; продолжительность перекрытия соответствует 3 и 10 секундам. Простое затухание первого и затем начало второго этот критерий не проходит. Для объективной проверки можно записать линейный выход и убедиться, что в участке перекрытия присутствуют сигналы обеих записей.
4. Переход не даёт щелчков, заметного пропуска звука, переполнения и зависания. Проверяются несколько последовательных смен, ручное переключение, пауза/возобновление, перемотка, конец плейлиста, разные частоты/форматы поддерживаемых штатной прошивкой файлов.

Запись экрана и аудиовыхода, версии двух тестовых файлов, установленное значение и SHA-256 считанного после установки firmware-раздела должны сохраняться как свидетельство проверки. До этих результатов структурно корректный `.img` нельзя именовать рабочим релизом.

## Установка без Rockbox и откат

В [исходниках Rockbox ipodpatcher CLI](https://github.com/mguentner/rockbox/blob/master/rbutil/ipodpatcher/main.c) есть отдельные действия `--read-partition` и `--write-partition`. На Windows синтаксис: `ipodpatcher.exe <DISKNO> <action> <file>`; `<DISKNO>` — текущий номер диска, который Windows может переназначить после переподключения. Сам `ipodpatcher` — инструмент записи, и эти действия **не устанавливают** Rockbox или его загрузчик. Поскольку UI может потребовать изменения RSRC, нужна запись **всего проверенного раздела**; `--write-firmware-bin` меняет только OSOS ([реализация](https://github.com/mguentner/rockbox/blob/master/rbutil/ipodpatcher/ipodpatcher.c)).

Последовательность после функционально подготовленного патча:

1. Перевести iPod в Disk Mode. Подтвердить `Get-Disk`: Apple iPod, USB, MBR, размер 30 005 821 440 байт; проверить привязку смонтированной data-партиции и первого firmware-раздела размером 98 574 336 байт. Не пользоваться номером диска из старой записи.
2. Считать текущий firmware-раздел **в новый файл** и сверить с оригинальным SHA. Оригиналы в проекте и `D:\` не открывать на запись.
3. Для будущего готового образа выполнить `py .\tools\build_partition_image.py verify --backup .\firmware\ipod_video_5.5g_30gb_stock_partition1.img --image .\build\crossfade-partition1.img` и сверить SHA из манифеста. Только после выполнения критериев реализации записать этот образ командой `ipodpatcher.exe <текущий DISKNO> --write-partition .\build\crossfade-partition1.img`.
4. **До первого запуска** снова считать firmware-раздел в новый файл и сравнить полный SHA-256 с установленным образом. Если не совпал — не продолжать загрузку, вернуться к исходной копии.
5. При неудаче или для отката снова определить текущий DISKNO в Disk Mode, проверить SHA оригинала и выполнить `ipodpatcher.exe <текущий DISKNO> --write-partition D:\ipod_video_5.5g_30gb_stock_partition1.img`. Считать раздел обратно в другой новый файл и требовать исходный SHA.

Для пункта 2 и проверки после записи добавлен `tools/verify_connected_ipod.py`. Он открывает PhysicalDrive **только с правом чтения**, сверяет USB/MBR/размер диска, букву FAT32 и границы раздела, затем сравнивает весь раздел с указанным файлом без промежуточной копии. После повторной проверки актуальных номера диска и буквы тома в PowerShell администратора:

```powershell
py .\tools\verify_connected_ipod.py --disk-number 1 --data-drive E --backup .\firmware\ipod_video_5.5g_30gb_stock_partition1.img --expected-image .\firmware\ipod_video_5.5g_30gb_stock_partition1.img
```

Число `1` и буква `E` здесь — пример текущего подключения, **не постоянные идентификаторы**. Для проверки после установки вместо `--expected-image` указывается проверенный `build/crossfade-partition1.img`, после отката — оригинальная копия. В обычном, не повышенном процессе Windows отказала инструменту в `GENERIC_READ` доступе к `PhysicalDrive1` (`WinError 5`), поэтому фактический read-back устройства из этой сессии не подтверждён. Скрипт ничего не записал.

[Документация проекта с испытанием на реальном 5.5G](https://github.com/BrandonDedolph/ipod-core/blob/main/core/docs/hw/08-boot-dock.md) описывает Disk Mode как режим ROM, доступный даже при испорченном OSOS: после перезапуска удержать Center/Select + Play/Pause. При нормальной реакции на кнопки перезапуск вызывается Menu + Center/Select, затем при появлении логотипа переключаются на Center/Select + Play/Pause. Если Disk Mode недоступен, самостоятельно повторять запись в неизвестный диск нельзя; далее используется штатное восстановление устройства и отдельная копия пользовательских данных.

В текущей работе команды записи не выполнялись и готовый образ на iPod не загружался.
