# Состояние четырёх задач на 18 октября 2026 года

Цель: кроссфейд 3–10 секунд и экран «Плавный переход» в штатной RetailOS 1.3 iPod Video 5.5G 30 GB. Этот файл описывает только подтверждённые результаты. Готового образа для установки пока нет.

## 1. Путь от декодера до I²S

При предыдущем подключении Windows показывала Apple iPod как USB-диск 1 размером 30 005 821 440 байт с MBR. Серийный номер совпал с номером, указанным владельцем; номер намеренно не записан в публичный репозиторий. Номер диска может измениться при переподключении. В текущем сеансе Windows видит только внутренний NVMe.

В OSOS с SHA-256 `784ae3d5540fd2f89e8c947b93629e97f62a06dc311d9745aab143e4db6bb251` подтверждена цепочка до буферизации I²S: литерал аппаратной базы `0x70002800` в `OSOS+0x25df58` → загрузка в `+0x25de8c` → конструктор `+0x18c85c` → связанная пара объектов `+0x1a3080(base+0x40)` и `+0x1a2790(base+0x80)` → callback `+0x1a2b74` → заполнение блока через `+0x1a2d60`. Обычный блок имеет размер `0x2400`; отдельный callback `+0x25a614` работает с половинами по `0x20000` байт. Интерфейс типа `1` также используется worker-ом `SpdifEbuScanner` `+0x18d3b4` через `+0x1e0d60`; одинаковый ID не доказывает, что ветка I²S получает PCM музыкального декодера. Просмотренные `TPCMQUEUE`, `FSbuf` и `StreamCacheReadTask` относятся к запросам/буферизации потока; они не доказывают доступ к началу следующей песни. Строки `mp3dec_sync`/`mp4_aacdec_sync` используются конструкторами объектов с общей таблицей методов `+0x66e0c4`, которая также обслуживает `FSsimple` и `RemoteResource`; эти имена не подтверждают декодеры. Исправленная классификация форматов показывает `.mp3` type 0 → metadata/frame-header parser `+0x2778f0`, а `.aa` type 6 → parser `+0x25f968`, в котором встречается tag `mp332`. Оба пути читают описание файла, но не подтверждают декодирование кадров в PCM или второй поток. Подробности — в [`AUDIO_PATH.md`](AUDIO_PATH.md) и [`AUDIO_XREF_NOTES.md`](AUDIO_XREF_NOTES.md).

Новая проверка HIBE проследила `TPCMQUEUE+0x5c` до provider-объекта RAM
`0x1086c6a0`. Таблица по `provider+0x30` содержит 32 descriptor-а; у 16
выделены буферы длиной `0x1200` каждый, со статусом 3 и адресами через
`0x4000` байт. Это согласуется с блоком `0x1200`, который рассчитывает
playback-path при 2 каналах, 16 битах и 1152 кадрах. Все 16 блоков содержат
ненулевые данные; их общий SHA-256 —
`a07a5af06f6a8c8319707935d78d4eb2dcba9e577b4dec8b5c94f9eab276520b`.
Worker `+0x23fc50` запрашивает один блок через `+0x722b20`, затем передаёт его
в обработку и форматное преобразование. Разбор состояния descriptor-а показал,
что consumer в наблюдаемом режиме требует статус 8, а статус 3 допускает
захват producer-ом. Все 16 выделенных буферов имеют статус 3; worker gate
`TPCMQUEUE+0xc8` равен нулю. Их ненулевое содержимое может быть остатком
предыдущего использования и не доказывает активное декодирование или вывод на
I²S. Сохранённый HIBE не показывает producer второго трека. Вывод воспроизводит
[`inspect_hibe_audio.py`](../tools/inspect_hibe_audio.py).

Тот же HIBE позволил восстановить таблицу из шести audio provider-ов по
`OSOS+0x63ee44`. Она привязана к player-объекту RAM `0x10939f60`, выбранный
индекс в сохранённом состоянии равен 0. У пяти объектов состояние 1, у шестого
— 2. В playback-событиях выбор через virtual slot `+8` фактически принимает
запрос типа 1 только у шестого объекта: у первых пяти этот slot всегда
возвращает ноль. Объект 5, передаваемый worker-у `+0x249390`, оказался
записывающим WAV: его код содержит литералы `RIFF`, `WAVE`, `fmt ` и `data`,
формирует заголовок и записывает аудиоблоки в файл. Поэтому этот найденный
путь не является музыкальным декодером и не даёт двух песен. Его IRAM-объект
при сохранённом эмуляторном состоянии не загружен. Таблица адресов и границы
вывода — в [`AUDIO_PATH.md`](AUDIO_PATH.md#сохранённый-реестр-audio-provider-ов).

Продолжение трассы разделило два режима `+0x285b70`: метод provider-а `+4`
ведёт к `+0x24a024` и циклу `+0x723000`, а метод `+0x0c` — к `+0x249390` с
WAV writer. Item provider-а 1 в первом режиме читает файл и преобразует
сэмплы в выходной PCM-буфер через `+0x160c34/+0x160bd8`. Цикл передаёт два
чередующихся буфера по адресам `0x149e3a08/0x149e4c08` в `TPCMQUEUE`:
runtime-вызов из `+0x722b88` фактически достигает `+0x732b1c`, после чего
descriptor становится готовым для consumer-а `+0x722b20`. Это реальный путь
**одного** файлового PCM-потока; точная связь типов provider-а 1 с форматами
музыкальной библиотеки, работа MP3/AAC и второй item остаются непроверенными.
Разбор — в [`AUDIO_PATH.md`](AUDIO_PATH.md#разделение-playback-и-wav-writer-подтверждённый-путь-одного-pcm-блока).

Для provider-а 0 восстановлена карта загрузки code/data из трёх областей OSOS
`+0x719b00`, `+0x71a80c` и `+0x71ee84` в IRAM. Его таблица методов
`0x400139dc` соответствует OSOS `+0x722860`; slot `+0x0c` ведёт к
`+0x71d614`, вызываемому тем же playback loop. Инициализатор выбирает
`0x240/0x480` кадров, типичный размер для сжатого аудио, но сам точный кодек
и связь с `.mp3`/AAC ещё требуют проверки. Важное ограничение: item
provider-а 0 создаётся по фиксированному IRAM-адресу `0x40013aa8`, а BSS
очищается при инициализации; второго независимого экземпляра сейчас нет.
Воспроизведение вывода — в [`AUDIO_PATH.md`](AUDIO_PATH.md#код-provider-а-0-загружаемый-в-iram)
и [`map_codec_overlay.py`](../tools/map_codec_overlay.py).

Проверка загрузчиков provider-ов 1–4 показала перекрытие IRAM-областей:
provider 0 и 3 совместно затрагивают 62 124 байта; даже provider 1 очищает
116 байт области, которую loader provider-а 0 заполняет кодом/данными.
Сам item provider-а 0 находится в другом месте, `0x40013aa8`. Повторное
создание codec item B, даже другого формата, может перезаписать код или
состояние A. Прежде чем проектировать hook для двух потоков, необходимо
реализовать независимые decoder state, file handle и буферы с проверенным
временем переключения. Числа воспроизводит `map_codec_overlay.py
--overlap-report`.

18 октября статическая реконструкция IRAM и исправление ручных косвенных
ARM7-вызовов позволили проследить provider 0 до обработки кадра:
`4000ae10 → 4000bad8 → 4000aaa4 → 4000a938/4000a6a0`.
Оба последних пути используют общие выходные ячейки `4000248c`, `40002510`,
рабочие области `40002514`, `40004f24` и объект очереди `149ee078`.
Значения воспроизводит `map_codec_overlay.py --output-state`.
Это уточняет необходимую изоляцию состояния; два музыкальных потока ещё не
запущены. Пересечение loader-ов не исключает отдельные контексты одного
кодека с общим кодом, но такой вариант требует проверки общих буферов и
callback-ов. Готовность к установке не изменилась: рабочего патча пока нет.

Последующий разбор связал очередь с именем `mp3dec_sync` в HIBE и её
callback `+0x1b1a10`. Через `+0x1249c4` он достигает stereo-синтеза
`0x40001dd0`, записывающего PCM16 с ограничением амплитуды. Найден отдельный
изменяемый контекст истории синтеза `0x40003714` размером не менее `0x1110`
байт. Его тоже необходимо разделить между A/B. Теперь есть конкретный путь
MP3 до PCM для одного источника; независимость двух источников и их совместное
воспроизведение всё ещё не проверены. Детали и ограничения — в AUDIO_PATH.md.

В том же снимке обнаружена отдельная очередь `mp4_aacdec_sync`, но у неё нет
прикреплённого callback-контекста; обе очереди имеют два слота и нулевые
счётчики. Это AAC и MP3, не два экземпляра одного декодера. Штатный stop-path
сигнализирует worker и ждёт снятия активного флага, что даёт кандидата на
момент без исполняемого callback; время жизни уже переданного PCM ещё не
проверено. Переключение A/B по-прежнему не доказано.

18 октября 2026 года разрешено значение двух слотов MP3-очереди по машинному
коду: `0x4001cf90` перед callback вызывает деление `completed / capacity`, а
остаток в R1 передаёт в callback как индекс слота. Helper `OSOS+0x82694`
проверен по его последовательности сдвинутых вычитаний; `OSOS+0x221508`
передаёт ему `queue+0x78` и `queue+0x40`. При capacity 2 это только два
перемежаемых рабочих слота одного callback. Дополнительная проверка provider-ов
`0x4000a6a0` и `0x4000aa5c` показывает, что вызов очереди расположен внутри
обработки одного item-а; второй проход определяется флагом item-а. Поэтому
слоты не следует трактовать как дорожки A/B, а ранее предложенная таблица
`owner[2]` не является обоснованной архитектурой. См. уточнение в
[`AUDIO_PATH.md`](AUDIO_PATH.md#обработчик-mp3-и-синтез-pcm).

В точном worker-коде `OSOS+0x221530` callback `+0x0c` исполняется один за
другом; completion-счётчик увеличивается после callback-а. Это подтверждает
синхронность заданий одного worker-а, но не безопасность переключения между
двумя источниками. Исследуемая схема — последовательно декодировать блок A,
затем B, сохранять их результаты отдельно и смешивать до DMA. До доказательства
безопасного переключения глобальных item/output/workspace указателей,
независимого synthesis state, повторного открытия B и запаса CPU эта схема
остаётся гипотезой; патча нет.

В том же снимке объект `RMIprimary` (`RAM 0x1093733c`, vtable
`+0x666348`) указывает полем `+0x4c` на этот `TPCMQUEUE`; статическая функция
`+0x25e148` инициализирует task `RMIprimary` и вызывает конструктор очереди
`+0x240614`. В HIBE найден один такой task, один queue и один playback/file
wrapper. Это описывает текущее состояние устройства, не доказывая запрет на
создание второго контекста другой веткой.

Дополнительный разбор `+0x132b14` и `+0x132c18` показывает чтение пар указатель/длина из очереди. Метод `+0x132b08` задаёт поле объекта `+0x30`; прямые вызовы найдены в `+0x18bf8c` и `+0x1b7568`. Объект воспроизведения хранит соседние указатели на `TPCMQUEUE` и объект, связанный с I²S, но просмотренный путь очереди передаёт управляющие сообщения, а не доказанные PCM-сэмплы. Подробные адреса — в [`AUDIO_XREF_NOTES.md`](AUDIO_XREF_NOTES.md). Не установлены конкретный музыкальный producer, формат PCM, момент предварительного открытия следующего трека и канал DMA.

Дополнительно проверен `HIBE` из оригинального раздела: диапазон `HIBE+0x800` побайтно совпадает со всем OSOS. Остаток содержит повторные ссылки на endpoint-ы `0x149dd4c8`, `0x149dd554`, `0x149dd638` и `0x149dd750` в структурах снимка RAM, однако самих областей памяти по этим адресам в HIBE нет. Эта находка подтверждает присутствие endpoint-ссылок в состоянии плеера, но не даёт кода микшера или буферов PCM; поэтому реализация кроссфейда всё ещё не обоснована. Подробности — в [`AUDIO_PATH.md`](AUDIO_PATH.md).

16 октября в чистом Ghidra-проекте отдельно проверен voice-пул по `+0x1b9168` и `+0x217a70`. Это четырёхслотовый путь запуска звуковых событий с выбором/вытеснением голоса. Новый разбор связал callback `+0x1d603c` с `+0x217cb8`: он обрабатывает один буфер и объекты этих четырёх голосов. Это mixer-подобный путь системных звуков; второй поток музыкального декодера в нём не найден. Runtime-заметки эмулятора отдельно связывают четырёхслотовый пул со щелчком колеса, но точное соответствие адресов пока не установлено. Этот путь не подтверждает кроссфейд двух композиций.

Последний разбор подтвердил, что путь `+0xb78b8` из обработчика смены текущей дорожки лишь строит `iPod_Control\Music\<имя>`. Инициализация playback-context проходит через `+0x10b894` → `+0xde500` → `+0xec31c`, после чего запрашивается динамический ресурс через `+0x13326c` и общий реестр. Зарегистрированный класс музыкального декодера и его PCM-интерфейс статически не определены; эта цепочка не даёт подтверждения второго декодера.

Инвентаризация точного `RSRC` нашла шесть ELF32-модулей VideoCore. Один экспортирует AAC decoder API, остальные — H.264/MPEG-4, MPlayer и вспомогательные модули. Экспортируемого MP3 decoder или отдельного `pcmplayer` API не найдено; это не исключает статически связанный или скрыто названный код. В OSOS есть имя `pcmplayer.vll` в таблице VideoCore-приложений и image-relative указатель на него, но прямой code xref не найден. Разбор полного HIBE показал runtime-пути `MPG4dec.vll`, `AACdec.vll`, `mplayer.vll` и `passthruhandler.vll`, но не `pcmplayer.vll`: имя `pcmplayer.vll` встречается в снимке только внутри скопированного OSOS. Это подтверждает запись в таблице OSOS, но не загруженный модуль. Снимок ограничен нижними 32 МиБ RAM и одним состоянием устройства. MPlayer импортирует `audio_play*` и `audioplus_register_callback`; это подтверждает аудиовывод VideoCore MPlayer, но не его связь с обычным музыкальным плеером, второй декодер или две дорожки. Детали и границы вывода — в [`AUDIO_PATH.md`](AUDIO_PATH.md).

Повторный read-only разбор Ghidra проследил общий путь создания playback-контекста до реестра объектов `+0x1f7d00/+0x1f7dc0`. Он работает со строковыми ключами и объектами, но не выявил зарегистрированный кодек или PCM producer; прямых xref/image-relative ссылок на конструкторы `mp3dec_sync` и `mp4_aacdec_sync` не найдено. Это сужает один кандидат, но не доказывает отсутствие косвенной загрузки. Независимый QEMU-проект умеет проводить штатный Video RetailOS по меню, но не моделирует звук; это может помочь только будущей проверке UI, не кроссфейда. Детали — в [`AUDIO_PATH.md`](AUDIO_PATH.md).

Дополнительный разбор worker-а `+0x285b70` подтвердил вызов `+0x249390` для
активного item. В переходном режиме объект `player+0x1950` берётся из
`TPCMQUEUE+0x78`; его vtable `+0x666284` имеет слот `+0x10`, ведущий в
`+0x1258c4`, который читает вложенный `FSbuf`. Полученный потоковый блок
передаётся item-у через слот `+0x18`. Это подтверждает путь файловых данных к
item-у, но не декодированный PCM на выходе. Для provider-а 5 item пишет WAV;
это исключает его как музыкальный decoder. Поле `+0x68` объекта получает
ссылку из `player+0x2e58`; в исследованной инициализации это адрес сервиса
`0x149e83a0`, не установленный PCM-output wrapper. Место PCM-микширования и
способность открыть следующий item до конца текущего трека не установлены.

Новая трассировка связала конструктор `TPCMQUEUE` `+0x240614` с инициализацией
playback-контекста (`+0x25e298`), а его vtable slot `+0x0c` — с worker-ом
`+0x23fc50`. Worker выделяет четыре записи/голоса, получает по одному буферу
на итерацию через внешний provider (`EXT_FUN_400189f4` → `OSOS+0x722b20` по
совпадению с IRAM) и передаёт блок в `+0x24ab48` и `+0x1a88dc`. Это
прослеженный аудиопуть с пока не доказанной связью с музыкой; два
музыкальных PCM-источника, связь с I²S callback и раннее открытие следующей
дорожки по-прежнему не подтверждены. Подробности — в
[`AUDIO_XREF_NOTES.md`](AUDIO_XREF_NOTES.md).

Дополнительная декомпиляция `+0x24ab48` уточнила этот участок: worker передаёт
один буфер, а интерфейсы обработки получают тот же указатель на вход и выход.
Функция `+0x20dd78` обрабатывает состояние/интерполяцию этого блока, но её
единственный caller — `+0x24ab48`; второго PCM-входа в вызове нет. Это
подтверждает обработку текущего блока, но не смешивание двух композиций.

Отдельно установлена только начальная конфигурация формата: `+0x24b458`
задаёт 2 канала и 16 бит, а `+0x24a024` рассчитывает размер как
`каналы × байты на сэмпл × 0x480` кадров (`0x1200` байт при начальных
значениях). Параметры могут меняться по метаданным item; знаковость и формат
DMA-слотов не подтверждены. Значение HIBE `0x2400` вдвое больше этого блока,
но содержимое и фактическую передачу между ними мы не установили.

В двух других состояниях `player+0x1950` указывает на аудиобуферные классы с
vtable `+0x668664`/`+0x666c80`: их слот `+0x10` получает буфер через внешний
интерфейс `EXT_FUN_4001da34`, а `+0x163eec` сохраняет указатель для обработки.
В событиях `0x0d/0x0e` диспетчер выбирает один такой wrapper, копирует в него
один из провайдеров `player+4/+8` и ставит только его адрес в `player+0x1950`;
worker затем получает один буфер через выбранный объект. Конструкторы
`+0x138e28/+0x143a10` включают разные режимы общего интерфейса. Смысл событий
и провайдеров не установлен. Код getter-а передаёт один адрес как источник и
назначение преобразователя, поэтому этот путь подтверждает выбор буфера, но не
смешивание; его связь с I²S callback тоже не установлена.

Повторная проверка `EXT_FUN_4001da34` с runtime-снимком IRAM теперь связала
его veneer `OSOS+0x844ec` с телом `OSOS+0x733800` (тот же код загружался по
`0x4001da34`). Единственный прямой caller `+0x163dc8` получает один указатель
от buffer-provider и передаёт его в `+0x1a88dc` как источник и назначение
одновременно. Helper выбирает запись из очереди, но содержимое записей и их
связь с музыкальным PCM либо I²S не установлены. Этот кандидат не даёт двух
входных потоков для кроссфейда; уточнённые детали приведены в
[`AUDIO_XREF_NOTES.md`](AUDIO_XREF_NOTES.md).

По сохранённому runtime IRAM также восстановлены provider-методы `+0x733410`
…`+0x73363c`: registry может содержать до восьми provider-объектов, выбор
делается по одному типу запроса и возвращает один индекс. Playback-события
`0x0d/0x0e` устанавливают один активный wrapper; второй PCM-источник в этих
ветках не используется. Сопоставление внешних вызовов повторяется скриптом
[`map_iram_aliases.py`](../tools/map_iram_aliases.py). Это уточняет штатный
маршрут одного источника, но не находит реального пути двух музыкальных
декодеров.

Повторная трассировка 16 октября уточнила выходную очередь I²S: поставщики
`+0x1b8100` и `+0x1b8178` передают пары указатель/длина в два кольца, которые
опрашивает callback `+0x1a2b74`; инициализатор `+0x1b7fdc` создаёт связанные
буферные узлы. Конструктор `+0x1b81d4` этой очередной системы вызывается при
инициализации I²S из `+0x25de8c`, что прямо связывает очередь с I²S-объектом.
HIBE-снимок связывает запрос типа `1` от `+0x1a2b74` с тремя объектами выхода
класса `+0x66d528`; callback `+0x1a2d60` передаёт буфер/длину методу
`+0x28ea7c`, который сохраняет их для задания; другой метод класса
`+0x28ea14` настраивает регистровую структуру. Виртуальная диспетчеризация
подтверждает, что обработчик задания `+0x124c44` вызывает слот `+0x58` этой
таблицы, соответствующий `+0x28ea14`, после постановки задания через слот
`+0x40` (`+0x28ea7c`). Это связывает очередь задания с передачей в I²S DMA,
но не устанавливает источник PCM. Это сильный кандидат выходной точки для
подмены блока. В runtime-снимке объект callback `0x1086ea10` связан с endpoint
`0x1086c814`, содержащим адрес регистра `0x70002840`, указатель буфера
`0x14a66560`, второй адрес слота `0x14a68960` и длину блока `0x2400`;
расстояние между слотами равно размеру блока. Содержимое, формат и принадлежность блока
штатному музыкальному декодеру, а также наличие одновременно декодируемой
следующей песни пока не доказаны. Поэтому безопасная точка кроссфейда всё
ещё не подтверждена; подробности внесены в
[`AUDIO_XREF_NOTES.md`](AUDIO_XREF_NOTES.md).

Дополнительно проверены два выходных endpoint-а, создаваемые `TPCMQUEUE`.
Обе ветки получают один и тот же буфер, а voice-pool callback меняет усиление
одного PCM-буфера и обслуживает до четырёх выходных слотов. Это не два
независимых музыкальных источника и не A/B микшер. Находка исключает этот
кандидат как готовый путь к двум песням; поиск второго музыкального decoder
producer остаётся открытым. Детали — в [`AUDIO_PATH.md`](AUDIO_PATH.md).

## 2. Микшер в реальном звуковом тракте

На компьютере есть работающий Python-прототип линейного смешивания PCM16 WAV. В точном OSOS найден voice renderer: `TPCMQUEUE` передаёт блок в callback `+0x1d603c`; тот вызывает `+0x217cb8`, где до четырёх voice-слотов рендерятся через `+0x146ba4`. Проверенный renderer `+0x146624` складывает PCM16 stereo voice с основным блоком с ограничением int16. Для provider-а 1 теперь прослежен producer PCM-блока до этой очереди, но соответствие формату композиции пользователя и одновременная работа второго декодера не доказаны. Подачи PCM дорожки B в этот микшер нет. Следующий технический шаг — установить MP3/AAC decoder, создать независимый контекст B и проверить его передачу в точку смешивания. Патч аудиотракта пока не собран.

## 4. Сборка, установка и проверка

Резервные образы в каталоге проекта и в корне `D:\` повторно проверены 16 октября: оба имеют размер 98 574 336 байт и SHA-256 `010bda520671d86a5a2cb010b57ee4484c980e54d97eb3e12621e08cde0423a3`. Штатные OSOS/RSRC повторно собраны в памяти; результат совпал с резервным разделом побайтно, ничего не записывалось. Повторная проверка подключённого устройства 16 октября подтвердила через Windows диск 1 `Apple iPod` размером 30 005 821 440 байт и FAT32-том E:, но `tools/verify_connected_ipod.py` по-прежнему не может открыть `PhysicalDrive1` на чтение из этого процесса (WinError 5). Установка на iPod не выполнялась: отсутствует проверенный патч OSOS/RSRC и собранный образ.

Добавлен офлайн-сборщик [`../tools/build_partition_image.py`](../tools/build_partition_image.py). Его `preflight` собрал штатные OSOS/RSRC в памяти и воспроизвёл исходный раздел побайтово, включая SHA-256. Сборщик может заменить компоненты только на равные по длине, пересчитать их поля суммы и проверить, что остальные байты раздела не изменились. Инструкция — в [`IMAGE_FORMAT.md`](IMAGE_FORMAT.md). Это проверка контейнера, а не работающий патч: изменённых OSOS/RSRC с кроссфейдом нет.

Перед установкой всё ещё нужны: реализация музыки и интерфейса в точном OSOS/RSRC; проверка их работы; загрузка и UI-проверка; аудиопроверка на переходе двух треков и при перемотке/смене частоты/отмене; способ возврата к исходной прошивке. Доступный эмулятор 5.5G RetailOS пока не моделирует звуковой кодек, поэтому не подтверждает кроссфейд на слух.

Дополнительная runtime-проверка эмулятором (исходники `siggifly/ipod-emulator`, commit `d39e850`) использовала синтетические MA446/NOR, тестовый диск с двумя сгенерированными WAV-файлами и точный OSOS выше. После бюджета 4 000 000 000 инструкций прошивка не прочитала ни одного из 17 кадров колеса; `WatchdogTask`-путь не дошёл до playback worker `+0x285b70`, file-stream `+0x1258c4`, audio-buffer методов `+0x163dc8/+0x163eec` или музыкального I²S callback `+0x1a2b74`; PP DMA сообщил 0 передач. Это показывает предел эмуляции/тестовой загрузки, а не отсутствие этих путей в штатном воспроизведении; runtime-путь музыки и точка микширования остаются неподтверждёнными.

## Проверка возможного переноса кода с других iPod

16 октября 2026 года проверены публичные источники о похожих реализациях. Руководство Apple для iPod nano 4-го поколения подтверждает штатную функцию Audio Crossfade (затухание конца одной песни и появление следующей), но описывает только On/Off и относится к другому устройству/поколению. Это не доказывает наличие соответствующего кода в RetailOS 1.3 для iPod Video и не даёт алгоритма с регулируемыми 3–10 секундами. Более новый проект RepriseOS меняет RetailOS 2.0.5 для Classic 6G–7G; он не поддерживает Video 5.5G/PP5021C, поэтому его патчи нельзя переносить в прошивку этого iPod. См. [Apple iPod nano 4th-generation guide](https://cdsassets.apple.com/live/6GJYWVAV/user/ma629_ipod_nano_4th_gen_userguide.pdf) и [osos-lab compatibility/build notes](https://github.com/lgreitis/osos-lab).

Эти сравнения сузили область поиска, но не закрывают ни один из четырёх критериев готовности: в точном Video OSOS ещё не выявлен производитель PCM следующей композиции, а работоспособная пара декодеров и точка управления переходом не установлены. Макет и структурный сборщик не заменяют функциональный патч.

## Уточнение callback-трассы

Проверены все 60 функций из относительной таблицы `+0x67e170…+0x67e264`,
которую исполняет диспетчер `+0x67e264`. Runtime-адрес `+0x25db30`, ранее
замеченный в тестовом логе, находится внутри функции `+0x25db1c` и лишь
заполняет статическую запись `mp3dec_sync`; соседний объект
`mp4_aacdec_sync` описывается функцией `+0x25e364`. Это регистрации/описания
объектов, а не подтверждённые вызовы декодеров. Сам тестовый прогон не дошёл
до меню и музыки, поэтому его периодические вызовы не подтверждают частоту
аудиоблока. В таблице и среди её функций не найдено подтверждения второго
музыкального потока или точки PCM-смешивания. Дамп и sweep остаются в
игнорируемом каталоге `build/`; детали — в [`AUDIO_PATH.md`](AUDIO_PATH.md).

Повторный разбор HIBE установил, что `TPCMQUEUE+0x78` указывает на один
объект playback wrapper `+0x666284` в сохранённом окне RAM; в нём виден
вложенный `FSbuf` `+0x674628`. Два соответствующих I²S DMA-слота содержат
только нули. HIBE захватывает 32 МиБ из 64 МиБ SDRAM 5.5G и не позволяет
проверить отсутствующие области; такой снимок не показывает PCM или
перекрывающиеся композиции. Read-only скрипт
[`inspect_hibe_audio.py`](../tools/inspect_hibe_audio.py) теперь выводит эти
указатели и занятость DMA-слотов.

## Дополнение: image-relative ссылки в таблицах методов

16 октября проверены нулевые результаты прежнего абсолютного pointer-scan.
В точном OSOS vtable содержит 32-битные image-relative значения: например,
`+0x668664` и `+0x666c80` ссылаются на `+0x163dc8`/`+0x163eec`, а
`+0x25d8c4` назначает эти таблицы объектам `0x149e3780` и `0x149e37e4`.
Getter/setter настроек также присутствуют как image-relative entries
`+0x66c94c/+0x66c950` → `+0x190b00/+0x1919d8`. Поиск
[`find_pointer_references.py`](../tools/find_pointer_references.py) расширен
на оба представления указателей. Эти ссылки помогают находить методы в
таблицах, но не выявляют callback колеса, не разрешают внешний аудио-сервис и
не подтверждают микширование или готовую прошивку.

В RSRC также найден модуль `transitions.vll` (`+0x459800..+0x465344`) с
экспортами `mp_transition_*` и `get_tran_fade_func_table`. Проверка его полного
списка экспортов/импортов показывает только обработку и вывод изображений
(например, `vc_image_*`, Dispman); `audio_play*` не импортируются. Поэтому
совпадения строк `Fade`/`transition` в RSRC относятся к видеослайд-шоу и не
дают штатного перехода между музыкальными композициями.

Повторная проверка уточнила поиск кодового зазора. Внутри OSOS есть полностью
нулевой диапазон `+0x6ca452..+0x7161a4` длиной 310 610 байт; Ghidra не нашла в
нём ни одной функции. Из четырёх ранее отмеченных ARM literal-load только два
загружают значения, численно похожие на RAM-адреса (`+0x3413c` → `0x1070adc2`
и `+0x6a8c4` → `0x106df241`); в соответствующих функциях они участвуют в
арифметике как константы, а остальные два значения находятся ниже RAM-базы.
Поэтому эти literal-load не являются подтверждёнными ссылками на свободный
участок.

Выровненный поиск нашёл 27 слов, чьи значения попадают в большой нулевой
диапазон, но часть совпадений — пары 16-битных значений или числовые константы.
В четырёх ссылках, отмеченных Ghidra, три исходят из таблицы значений в
`+0x6b95c8..+0x6b95d0`, а одна (`+0x730e44` → `+0x6e2440`) лежит в таблице
адресов, назначение которой пока не установлено. Это делает нулевой промежуток
кандидатом на статическое размещение кода, но не доказывает, что все адреса в
нём не используются косвенно во время работы.

Отдельно найден меньший нулевой диапазон
`OSOS+0x733c98..0x7358c0` (7 208 байт). Хотя read-only Ghidra-проверка не нашла
в нём функций или прямых ссылок, точная трасса IRAM сопоставила область
`OSOS+0x7335cc..+0x7358c0` с копией helper-а в IRAM `0x4001d800..0x4001faf4`.
Следовательно, этот диапазон входит в копируемый runtime-образ; его нулевое
содержимое не означает, что он свободен. Использовать его можно рассматривать
только после проверки границ/жизненного цикла этого overlay и всех его копий.
Сканер [`inspect_osos_code_caves.py`](../tools/inspect_osos_code_caves.py)
показывает нулевые диапазоны, но не знает о копировании overlay в IRAM.

Внутри большого нулевого диапазона выделено более узкое окно
`OSOS+0x712000..+0x7161a4` размером 16 804 байта. Оно начинается на следующей
границе 4 КиБ после последнего address-like значения `+0x711070`; само окно
полностью нулевое, не содержит выровненных слов со значениями-адресами внутрь себя и не
пересекается с известными OSOS→IRAM копиями provider-ов 0–4 и runtime helper-а.
Точный Ghidra-скан дал 0 функций и 0 прямых ссылок. Это текущий **предварительный
статический резерв кода** без увеличения длины OSOS.

Отдельная сверка 27 синтаксических кандидатов ручного ARM/pointer-сканера
уточнила картину: среди них 17 branch-pattern и 10 слов-указателей, но все
адреса-источники лежат вне функций, известных Ghidra; заранее определённой
инструкцией был только один адрес. Прямых xref-ов в окно Ghidra тоже не нашла.
Эти совпадения поэтому считаются неподтверждёнными и, вероятно, ложными
срабатываниями по данным. Проверка сужает статический риск, но не заменяет
проверку вычисляемых ссылок, загрузчиков и runtime-владельца диапазона.
Read-only разбор: `build/ghidra-cave-reference-classification-20261018.log`;
командный вывод сканера: `build/osos-code-cave-audit-20261018.log`.

Подготовлен guarded placer `tools/inject_osos_payload.py`, который проверяет
неизменённый backup, нулевое окно и предел 16 804 байта, а затем пишет только
новый OSOS в `build/` с манифестом. Сам payload кроссфейда ещё не собран, поэтому
placer не запускался и образ не создан.

Окно всё ещё не сертифицировано как свободное runtime-место: статические проверки
не исключают вычисляемых указателей, копирования другим подсистемным loader-ом
или динамического использования в другом состоянии. До записи payload нужно
установить владельца диапазона, проверить загрузку/возврат и подтвердить, что
hook не пересекается с активными задачами/overlay. Поэтому безопасное runtime-
место и образ-кандидат пока не готовы.

## Проверка увеличения OSOS

В копии firmware-раздела после конца HIBE остаётся 51 107 840 байт. Read-only
планировщик `tools/plan_partition_relocation.py` показывает, что при условном
росте OSOS на 1 МиБ RSRC, AUPD и HIBE можно расположить на 1 МиБ дальше, оставив
50 059 264 байта в конце раздела. Это доказывает только наличие места в
контейнере. Образ не собирался и не менялся.

Каталог загружает OSOS по адресу `0x10000000`; его длина заканчивается на
`0x10736000`. У HIBE размер ровно `0x800` байт заголовка плюс 32 МиБ снимка
RAM, начало которого совпадает с OSOS. В следующих 2 МиБ снимка после OSOS
57,5% байтов ненулевые; самый длинный нулевой диапазон — 135 012 байт.
Это не карта heap allocator-а и не подтверждение свободной RAM. Добавление
байтов OSOS в этот диапазон может занять уже используемую память; формат
resume из HIBE после расширения также ещё не установлен.

Уточнение по allocator-у: глобальные ячейки OSOS `+0x11ca48`, `+0x11ab98` и
инициализатор `+0xd2e54` указывают на ячейку RAM `0x1081da00`; её первое слово
содержит адрес heap-структуры `0x10870154`. Гипотетический рост OSOS на 1 МиБ
перекрыл бы ячейку `0x1081da00`. В HIBE pool-диапазоны настроенного heap-а
занимают `0x10a0ffa4..0x11effff8` и `0x1086c158..0x1087014c`. Ненулевые байты
снимка сами по себе не являются картой свободных блоков; отдельная проверка
списка ниже уже восстанавливает его состояние для сохранённого HIBE-снимка.
Это не делает область после OSOS резервом кода: рост image range заденет
runtime-состояние, а формат resume после такого роста не установлен.

Read-only скрипт [`../tools/inspect_hibe_heap.py`](../tools/inspect_hibe_heap.py)
проверяет цепочку указателей, границы двух heap-регионов и весь двусвязный
список блоков. В сохранённом HIBE он нашёл 47 свободных блоков, всего
4 962 392 байта (22,6% настроенных регионов); крупнейший непрерывный блок —
4 641 944 байта. Сумма совпадает со счётчиком heap-а. Один decoder item занимает
`0x3bec` байт; штатный allocator округляет такой запрос до `0x3bf0`, и крупнейший
снимочный блок его вмещает. Это показывает потенциальный запас для
дополнительного контекста и рабочих буферов. Но HIBE фиксирует одно сохранённое
состояние: это не измерение доступной памяти во время активного воспроизведения
и не проверка безопасного выделения второго MP3 item-а.

Следовательно, расширять OSOS в соседнюю RAM нельзя считать необходимым
способом получить место: внутри исходного образа уже есть нулевые диапазоны,
включая 7 208-байтовый участок без найденных прямых ссылок. Их пригодность для
патча требует проверки косвенных обращений и runtime-поведения. Сборщик пока
оставляет длины и смещения неизменными; скрипты анализа не создают образ и не
являются рекомендацией к установке.

## Проверка возможности использовать второй ARM-кор

В точном OSOS нашлись обращения к регистрам `CPU_CTL`/`COP_CTL` по
`0x60007000`/`0x60007004` и проверки идентификатора процессора по
`0x60000000`. Ghidra проследила часть этой логики в функциях
`OSOS+0x1b6ee4` и `OSOS+0x1b88b0`; в ней выбираются core-зависимые значения
управления и ожидания. Это доказывает наличие в образе кода, учитывающего оба
ядра, но не доказывает, что COP свободен в штатном runtime, что этот путь
достижим при проигрывании музыки или что его можно безопасно занять вторым
декодером. Поэтому использовать COP как готовый вычислительный ресурс для
кроссфейда пока нельзя. Отдельный bare-metal проект с собственным MP3
декодером не является модификацией RetailOS и эту неопределённость не снимает.

Последняя проверка не изменила статус четырёх критериев: музыкальный источник
B, безопасный wheel-event callback, доказанная ячейка настройки и проверенный
runtime hook всё ещё не соединены в патч. Никакие байты прошивки не изменялись;
собираемого образа для установки нет.

Factory provider-а 0 повторно вызывает loader, инициализирует MP3-контекст в
статической области item-а и кладёт его адрес в `0x40013a64`. Item/BSS занимает
`0x3bec` байт, а вложенный ring buffer использует caller-provided storage.
В RetailOS найден общий heap allocator и подтверждён caller, который использует
возвращаемый им адрес. Это даёт путь выделить отдельный блок B, если вызвать
вложенный constructor без повторного loader-а; такую инициализацию ещё не
реализовали и не запускали. `map_codec_globals.py`
воспроизводит зафиксированные IRAM-ссылки на общие output-ячейки, callback,
очередь и item. Карта пока ограничена разобранными функциями. Полный layout и
второй экземпляр не реализованы.
Сверка списка allocator-а в HIBE подтверждает, что в сохранённом состоянии
есть свободные блоки, включая один около 4,64 МиБ. Поэтому «расширять» файл
OSOS ради RAM не требуется для самого размещения будущих буферов; корректный
механизм — запросить память у штатного heap во время работы. До подтверждения
heap-состояния при проигрывании, второго decoder-контекста и его побочных
эффектов этот запас остаётся только статическим свидетельством, а образ
кроссфейда не готов.
Уточнение от 18 октября: вложенный constructor привязывает `0x800`-байтовый
ring buffer к item по смещению `+0x3395` и очищает приватные рабочие области; в
проверенных подфункциях явного запуска OS-задачи нет. Сырые инструкции helper-а
`0x4000baac` (`OSOS+0x71e2b0`) показали обычный возврат после инициализации,
без косвенного вызова. Инициализатор item-а `+0x127df4` открывает stream и
обращается к общему service slot 5, поэтому безопасно подготовить второй
playback item пока не доказано. Это уточняет конструктор B, но не создаёт второй
источник PCM и не меняет статус готовности.

Прослеженная функция смены трека `+0xeb610` закрывает текущий item в `player+0xa9`
и обнуляет это поле до открытия нового: стандартный player не держит A, пока
готовится B. Открытие MP3-item-а также получает hardware/service slot 5 общего manager-а;
в сохранённом HIBE slot занят одним объектом с vtable `OSOS+0x671084`, чьи
методы затрагивают общий аудиовыход. Это дополнительные ограничения для
стандартного пути, не доказательство невозможности отдельного низкоуровневого
decoder B. `inspect_hibe_audio.py` теперь печатает состояние этого 15-slot
registry из оригинального backup.

Сканер точного OSOS обнаружил два ARM literal-use для `0x40013a64`: фабрика
пишет туда active decoder state, MP3 callback читает. Это даёт конкретную
ячейку для будущего переключения состояния, но не доказывает, что все прочие
общие данные и отложенные callback-ы можно переключить безопасно.

Дополнительная проверка точных инструкций уточнила, что история PCM-фильтра
является передаваемым контекстом размером `0x1110` и может храниться отдельно.
Но полный MP3 init пишет в общие `mp3dec_sync` и scratch-буферы. Это подтверждает
наличие частного состояния для клонирования, одновременно показывая, что одного
выделения heap block недостаточно: producer B и безопасная диспетчеризация
пока не реализованы. Образ и резервная копия остаются без изменений.

## Уточнение service slot 5 и Settings UI — 18 октября 2026 года

Статическая трассировка второго MP3 initializer-а `+0x127df4` установила, что
после открытия stream он вызывает методы `+0x3c` и `+0x30` общего service
slot 5. У объекта из HIBE vtable `+0x3c` указывает на IRAM `0x40000e44`; его
код побайтно сопоставлен с `OSOS+0x716fe0` и меняет состояние аппаратного
аудиосервиса. Это подтверждает риск повторного полного открытия B при
воспроизведении A, но не даёт готового обхода и не подтверждает второй PCM.

Для штатного Settings найдено 18 строк; русские подписи в OSOS хранятся в
UTF-8. Экран «Предел громкости» использует View `17538` без `Cntl`-элемента,
поэтому его нельзя автоматически считать универсальным регулятором времени.
Подробная карта меню находится в [`ui/stock_resource_map.md`](ui/stock_resource_map.md).

Новый Ghidra скрипт `tools/ghidra/DumpIramFunctions.java` позволяет
декомпилировать адреса из сохранённого IRAM-снимка. Образ-кандидат, который
можно установить, всё ещё не собран.

Дополнительно оценён обход второго одновременно работающего декодера:
накопить невыведенный PCM-хвост A в look-ahead ring, затем переиспользовать
тот же decoder для B и смешивать сохранённую очередь A с очередью B. На
44,1 кГц, stereo PCM16 10 секунд требуют 1 764 864 байта при выравнивании на
блоки по 1152 кадра. Это помещается в крупнейший свободный блок 4 641 944 байта
из HIBE-снимка, но размер свободной памяти во время проигрывания неизвестен.
Worker, который стабильно поддерживает такой запас впереди вывода, расширение
descriptor ring и безопасное повторное открытие B без остановки slot 5 пока
не доказаны. Поэтому этот путь — новая архитектурная гипотеза, а не готовый
патч. Расчёт находится в `tools/crossfade_memory_budget.py`, детали — в
[`AUDIO_PATH.md`](AUDIO_PATH.md#возможная-схема-с-одним-декодером-и-pcm-look-ahead).

Vtable снимка HIBE связала TPCMQUEUE worker с `OSOS+0x23fc50`; его цикл
обрабатывает запрошенный блок, сбрасывает `queue+0xc8` и ждёт событие на
`queue+0x1554`. Это показывает, что look-ahead нельзя получить одним лишь
расширением буфера: ещё требуется организовать подачу нескольких секунд PCM
вперёд, не нарушив handshaking очереди. Событие-триггер и рабочий режим
заполнения ring-а не установлены. Read-only декомпиляции находятся в
игнорируемом `build/ghidra-audio-worker-flag-offset.log` и
`build/ghidra-tpcmqueue-vtable-methods-20261018.log`.

Очередь `+0x1554` получает сообщения от нескольких обработчиков через
`OSOS+0x23f400`; класс сообщения использует vtable `OSOS+0x678034`. Вызовы
включают смену состояния интерфейса, поэтому связь с каждым запросом аудиоблока
нельзя выводить из одного только wake-up. Источник сигнала, который ставит
`queue+0xc8`, ещё не прослежен; дополнительные read-only декомпиляции лежат в
игнорируемом `build/ghidra-audio-worker-event-*.log`.

### Проверка идеи расширить OSOS ради буфера — 18 октября 2026 года

Размер `queue+0xc8` нельзя трактовать только как булев флаг: в HIBE всё
32-битное поле равно `0x00000400`, а worker читает и сбрасывает его младший
байт. Добавлен read-only скрипт Ghidra
`tools/ghidra/FindByteStoreOffset.java`; поиск инструкций записи со смещением
`0xc8` нашёл 61 статический кандидат. Из byte-store-ов worker содержит запись
сброса в `OSOS+0x23fdfc`; два других byte-store-а принадлежат отдельным
таймерным объектам. Это не установило источник установки младшего байта, а
найденные word-store-ы требуют дальнейшей проверки базового объекта и
передаваемого значения. Скрипт можно повторить так:

```powershell
& $ghidra (Join-Path (Get-Location) 'build\ghidra-projects') RetailOS_1_3 `
  -process osos.bin -noanalysis -readOnly `
  -scriptPath (Join-Path (Get-Location) 'tools\ghidra') `
  -postScript FindByteStoreOffset.java 0xc8
```

Следующий поиск проверил вариант, где поле вычисляется через `ADD`, а затем
записывается через регистр базы. Единственный кандидат `OSOS+0x16f850` находится
в `+0x16f7dc`: функция строит вложенный объект с очередью событий и таймерными
полями; ссылок на `TPCMQUEUE` в этом пути нет. Кандидат исключён как посторонний,
а setter младшего байта `TPCMQUEUE+0xc8` пока не найден. Read-only результат —
`build/ghidra-queue-flag-candidate.log`; поиск воспроизводится командой
`FindCalculatedOffsetStores.java 0xc8` в том же Ghidra-проекте. Скрипт
[`../tools/ghidra/FindCalculatedOffsetStores.java`](../tools/ghidra/FindCalculatedOffsetStores.java)
сопоставляет только короткие цепочки `ADD` → `STR*`, поэтому его совпадение
является кандидатом, а не доказательством идентичности структуры.

Дополнительно уточнён уже найденный post-decode voice mixer: `+0x217a70` берёт
слот, `+0x145f90` связывает его с PCM source descriptor, а `+0x146258` запускает
воспроизведение; `+0x146624` суммирует PCM16 stereo с музыкальным блоком.
`+0x217cb8` сначала применяет ramp основного PCM через `+0x2179f0`, затем
рендерит voice-слоты, где `+0x146520` отдельно меняет уровень каждого voice.
Это подтверждает штатные точки для двух независимых уровней A/B, если имеется
валидный PCM source B. Сам producer следующей песни, создание descriptor-а для
сырого PCM и продолжение B после его стартового буфера не реализованы. Детали и
ABI-поля — в [`AUDIO_PATH.md`](AUDIO_PATH.md#подтверждённый-voice-pcm-mixer-в-playback-callback);
read-only дампы — `build/ghidra-voice-source-api.log` и
`build/ghidra-crossfade-gain-control.log`.

Новая read-only трассировка `+0x23fc50`/`+0x23f444` показывает, что voice worker
получает source-элементы из отдельного provider-а, а `+0x146ba4` поддерживает
позицию и переход к следующему descriptor-у. Это кандидат на потоковую подачу
PCM дорожки B через штатный voice renderer, что может избежать многомегабайтного
PCM look-ahead. Безопасное создание/подключение пользовательского provider-а,
его формат и выдача данных вторым MP3 producer-ом не доказаны. Это направление
для статического прототипа, а не готовая функция; новые дампы сохранены в
`build/ghidra-voice-stream-probe-20261018.log` и
`build/ghidra-voice-provider-probe-20261018.log`.

Расширять дисковый размер OSOS ради аудиобуфера не следует. PCM на 3–10 секунд
при 44,1 кГц stereo PCM16 занимает от 529 920 до 1 764 864 байт с текущим
выравниванием блоков. Это должна быть runtime-аллокация в heap. План роста OSOS
на 1 МиБ с перемещением следующих компонентов заканчивается адресом RAM
`0x10836000` и пересекает известный allocator object `0x1081da00` на
`0x18600` байт; увеличение файла само по себе не создаёт свободную RAM. В HIBE
есть большой свободный блок только в одном сохранённом состоянии, поэтому
доступность такого heap-буфера во время музыки всё ещё не подтверждена.

Для отдельного MP3 item B известны ещё 15 340 байт item-а и 4 368 байт
частной filter-history. Обновлённый калькулятор показывает их отдельно и
прибавляет к PCM look-ahead: от 549 628 байт для трёх секунд до 1 784 572
байт для десяти секунд. Это нижняя оценка, не включает stream/cache и allocator
overhead и не гарантирует непрерывный блок в активном heap.

### Уточнение кэш-контекста следующего трека — 18 октября 2026 года

В точной RetailOS повторно разобраны `+0x1153d4`, `+0x87cec` и `+0x92750`. При ошибке первоначального чтения новый cache-context в обычном режиме проходит по всем активным контекстам и закрывает их дочерние файловые дескрипторы перед попыткой чтения меньшего диапазона. Также успешное открытие сохраняет cache-context по смещению `player+0x29d0`, поэтому второй open может перезаписать указатель текущего трека. Наличие нескольких файловых кэшей не гарантирует независимость дорожек.

Изучается безопаснее завершаемый отказ B: в отдельной копии инициализатора передать `0` только как третий аргумент в `+0x1153d4`, чтобы при нехватке памяти не закрывать handles остальных контекстов; отдельный вызов `+0xb057c` инициализатора при этом сохранить. Это лишь кандидат для статического прототипа: он может отказать в открытии B, а поле `player+0x29d0`, ссылки и обращения потребуют отдельной трассировки и runtime-проверки. Read-only декомпиляция: `build/ghidra-cache-multipath-condition-20261018.log`; детали добавлены в [`AUDIO_PATH.md`](AUDIO_PATH.md#условие-очистки-при-создании-второго-cache-context).
