# План памяти для поточного кроссфейда

Этот план отвечает на вопрос, где разместить PCM для перехода 3–10 секунд в
RetailOS 1.3 на iPod Video 5.5G с диском 30 GB. Он описывает архитектуру и
проверенные границы; код второго декодера и устанавливаемый образ пока не
готовы.

## Где брать память

Не нужно увеличивать длину OSOS на диске, чтобы получить RAM. Прошивка
загружается по адресу `0x10000000`; её длина на диске одновременно определяет
область RAM, занимаемую образом. Рост на 1 MiB сдвинул бы конец образа до
`0x10836000` и пересёк бы известную структуру штатного allocator-а по адресу
`0x1081da00` на `0x18600` байт. Хотя контейнер раздела физически имеет место,
это не свободная область RAM и не безопасное расширение.

Штатный heap предоставляет функции `OSOS+0x25a974(size)` для выделения и
`OSOS+0x25a8f4(ptr)` для освобождения; вызовы добавлены в runtime ring helper.
Интеграция должна запросить память через этот allocator после подготовки
перехода и до аудиоколбэка. Если запрос
не удался, переход выключается для этой пары треков, а штатное воспроизведение
продолжается. Из реального PCM callback нельзя вызывать аллокатор или ждать
I/O: callback должен только обрабатывать готовые блоки.

У экспериментального playback hook-а есть отдельный статический B scratch
размером 4 608 байт для одного блока в 1 152 stereo PCM16 frames. Он лежит в
непроверенном runtime code window по `0x10714988`; это не дополнительная RAM и
не заменяет heap для независимого decoder state, resource-ов и PCM-ring.

## Сколько памяти требуется

Длительность кроссфейда — это число кадров, на которых меняются коэффициенты
двух потоков. Она не равна глубине буфера. Если существуют два независимых
producer-а, можно смешивать блоки по мере поступления. Для 44,1 кГц, stereo
PCM16 один блок на 1152 кадра занимает 4608 байт. Четыре блока второй дорожки
содержат 18 432 байта PCM и дают около 104 мс очереди. Реализованный кольцевой
буфер добавляет 20 байт заголовка и 4 байта sentinel-кадра, всего 18 456 байт;
во время перехода микшер обрабатывает блок за блоком все 3–10 секунд.

Текущий нижний subtotal B-стороны при четырёх блоках:

| Часть | Байты | Статус оценки |
| --- | ---: | --- |
| MP3 item и filter history | 19 708 | Размеры прослежены в OSOS |
| Provider-0 workspace | 15 376 | Весь очищаемый BSS; владение экземпляром не доказано |
| 4 PCM блока и ring overhead | 18 456 | Геометрия блока подтверждена; второй producer не реализован |
| Минимальные descriptor-ы | 304 | Не менее 76 байт на descriptor; полный размер неизвестен |
| Track-resource объект | 700 | Размер прослежен в factory |
| MP3 callback/queue объект | 164 | Минимум до `queue+0x80`; динамическая копия не проверена |
| MP3 worker stack request | 1 792 | Значение `queue+0x10 = 0x700`; allocator-владелец не установлен |
| **Subtotal** | **56 500** | **С кандидатами sync object/stack; без полного cache, PCM descriptor extent, DMA handoff и allocator overhead** |

Этот subtotal также не включает отдельный RMIprimary/FSbuf parent для B.
`FUN_1024b5bc`/`FUN_10216b4c` строят stream-object у `parent+0x2e60`; видимые
инициализатор и worker используют родительскую область до `+0x90c5`. Если B
получит отдельный parent block, выровненная нижняя оценка его размера —
`0x90c8` (37 064 байта), а subtotal станет 93 564 байта. Нужна ли полная копия
parent-а или достаточно отдельных полей, пока неизвестно; размер внутренних
stream/cache ресурсов также не установлен.

Новая проверка конструктора `FUN_10216b4c` добавляет ещё один потенциальный
расход. При штатном создании player-а RetailOS передаёт backing address
`0x14983100` (native RAM `0x10983100`) и размер `0x40000` байт; конструктор
сохраняет их во внутренних полях `+0x4070/+0x407c`, а chunk size `0x8000` — в
`+0x4080`. HIBE показывает 8 таких блоков в 256-КБ диапазоне; этот диапазон
уже занят штатным FSbuf и не является свободным запасом для B. Если у B должен
быть отдельный FSbuf без совместного буфера A, к предыдущему subtotal нужно
добавить ещё 262 144 байта: кандидат станет 355 708 байт до неизвестных cache,
descriptor и allocator расходов. Это бюджетный сценарий, но не доказательство,
что второй FSbuf безопасно сконструировать или что именно все эти байты должны
быть приватны.

Это не доказанный резерв и не гарантия свободной памяти. Это целевой порядок
величины для потоковой схемы, если удастся создать независимое состояние B.
Фактический объём нужно измерить во время воспроизведения и проверить на
физическом устройстве. Предыдущая оценка 54 520 байт включала provider state,
track resource и четыре PCM-блока с минимальными descriptor-ами, но не отдельные
sync object и stack request.

Для схемы с одним декодером нужен look-ahead из уже декодированного PCM. Буфер
10 секунд при том же формате занимает 1 764 864 байта с выравниванием на целые
блоки. Это отдельная, значительно более крупная архитектура; она также требует
доказанного способа заранее получить и удержать нужные аудиоданные. Текущий
worker обрабатывает PCM блоками по запросу, поэтому такой запас не следует
считать доступным или готовым.

Повторить расчёт можно командой:

```powershell
py .\tools\crossfade_memory_budget.py --queued-blocks 4
```

Сравнение с наибольшим свободным блоком HIBE — только проверка сохранённого
снимка простоя. HIBE показывает 4 641 944 байта в крупнейшем свободном блоке,
но не измеряет heap при активном проигрывании.

## Почему пространство ещё не превращается в звук

В OSOS найден PCM callback `+0x1d603c`; перед штатным voice mixer-ом
`+0x217cb8` есть кандидат на wrapper в `+0x1d606c`. Это подходящая точка для
смешивания уже полученных двух PCM-блоков, но она не создаёт второй поток.

Provider 0 использует фиксированные ячейки IRAM для общей очереди и рабочих
буферов (`0x149ee078`, `0x4000248c`, `0x40002510`, `0x40004f24` и
`0x40002514`). Его обычная инициализация копирует overlay и очищает общий BSS.
Поэтому повторно вызвать обычный factory для B нельзя: он может затронуть
состояние A. Вложенный конструктор декодера существует, но отдельный объект
сам по себе не отделяет эти общие ячейки, очередь, файл и service slot 5.

В точном OSOS объект `mp3dec_sync` инициализируется одной статической
функцией `+0x25db1c`. В сохранённом HIBE callback находится по RAM
`0x109ee058`, а очередь — по `0x109ee078`; её ёмкость равна 2. Метод callback
vtable `+0x0c` — это `OSOS+0x1b1a10`, а его приватный filter context указывает
на фиксированный IRAM `0x40003714`. Этот же callback читает единственную
ячейку активного decoder item по `0x40013a64`. Значит, два штатных слота
очереди обслуживают один callback, один filter context и один активный item.

При этом в HIBE есть отдельный объект `mp4_aacdec_sync`. Его инициализатор и
инициализатор `mp3dec_sync` записывают в поле `queue+0x3c` один адрес
`RMIprimary+0x15c` (`0x14937498`, native RAM `0x10937498`); сами очереди
расположены отдельно и имеют stack sizes `0x700` и `0x2c8`. В снимке MP3 queue
имеет callback, AAC queue — нет. Это подтверждает общий task context pointer,
но не показывает, что дополнительная MP3 queue сможет получить отдельный
worker и независимые codec state. Инспектор выводит эти поля командой:

```powershell
py .\tools\inspect_hibe_audio.py .\firmware\ipod_video_5.5g_30gb_stock_partition1.img
```

Worker выполняет callback-и последовательно и увеличивает счётчик завершённых
заданий после возврата из callback. В теории это позволяет подавать задания A
и B по одной очереди, если каждому занятому слоту заранее назначен владелец,
а callback выбирает соответствующие item, filter state и выходной PCM-buffer.
В штатной прошивке такого назначения владельца нет. Отдельная очередь потребует
создать второй корректно связанный sync object и проверить, может ли
существующий audio worker обслуживать его; при необходимости понадобится
отдельный worker. Статическая инициализация связывает текущий объект с audio
worker и задачей RMIprimary, но обслуживание нескольких таких очередей не
подтверждено. Ни одна из этих схем не реализована и не проверена на устройстве.

### Кандидат: отдельное состояние provider-а без повторной загрузки overlay

Фабрика provider-а 0 (`OSOS+0x1a8ff8`) вызывает loader `+0x839c0`, задаёт
базу состояния `0x40013aa8`, вызывает внутренний MP3 constructor `0x4000bc9c`
с адресом `base+0x44`, а затем записывает возвращённый item в единственную
глобальную ячейку `0x40013a64`. Повторный вызов фабрики не подходит: loader
очищает IRAM-контекст и factory снова пишет в то же provider state.

В самом constructor-е `0x4000bc9c`, восстановленном из точного overlay
`OSOS+0x71e4a0`, инициализация идёт от переданного указателя и создаёт
вложенные decoder/filter объекты. Предварительный scan literal-слов трёх
provider-0 overlay ranges не нашёл прямых ссылок из кода в диапазон его
provider-BSS `0x40013aa8..0x40017694` (15 340 байт); абсолютные ссылки кода
ведут в общую очередь/scratch и отдельные global cells. Это делает heap-копию
provider state плюс прямой вызов внутреннего constructor-а кандидатом для B,
который не перезагружает overlay. Scan не исключает вычисляемые обращения,
скрытые зависимости constructor-а или недостающие поля и не доказывает
работоспособность такой копии.

Чтобы этот кандидат стал вторым музыкальным потоком, патчу всё ещё нужно:
открыть независимый file resource/cache для следующего трека; дать B отдельный
provider/item и synthesis history; назначить каждый queued job слоту A или B
и выбирать его active-item cell `0x40013a64`, filter context
`0x40003714` и output в serialized callback; подавать PCM B в кольцевой буфер;
смешивать блоки до I²S. Существующая очередь с двумя слотами и точка
PCM-сложения делают эту схему предметной, но она пока не реализована и не
испытана. Повторить карту overlay можно командой:

```powershell
py .\tools\map_codec_overlay.py .\firmware\extracted\audio-analysis\osos.bin `
  0x4000bc9c 0x4000a938 0x4000ae10 0x4000aaa4 0x4000bad8 --output-state
```

### Кандидат: получить следующий track object и открыть его ресурс отдельно

В обычном переключении `FUN_100ac4c4` (`OSOS+0xac4c4`) берёт активный track
object из `player+0x2a4`, передаёт его track id в selector `FUN_101968c0`
(`+0x1968c0`), а потом при необходимости передаёт найденный объект в
`FUN_100ac6f4` (`+0xac6f4`). Именно `FUN_100ac6f4` вызывает
`FUN_100eb610` и начинает менять активный track/player; вызывать эту часть при
предварительной подготовке B нельзя.

Selector использует singleton cursor `FUN_10196418`: тот лениво выделяет
объект размером `0x90` и создаёт его через `FUN_10196de0`. Инициализатор
`FUN_101960b0` очищает собственный cursor и подготавливает query context;
`FUN_101968c0` ищет track object через каталог, проверяет пригодность через
`FUN_10235b68` и, если задан флаг `4`, записывает выбранный track key в
`cursor+0x14`. Флаг `4` также меняет аргумент направления поиска с `4` на `1`,
поэтому простое снятие этого бита не подтверждено как эквивалентный запрос.
Отдельный cursor может позволить заранее получить следующий объект, но его
инициализацию тем же query и связь с текущей очередью воспроизведения ещё нужно
восстановить. Также не доказано, какие поля каталога меняются при поиске.

Функция `FUN_10196de0` инициализирует переданный ей cursor; singleton getter
перед этим выделяет для него `0x90` байт. Это делает второй cursor технически
правдоподобным, но штатная прошивка создаёт и хранит только глобальный экземпляр.
У selector-а `FUN_101968c0` видимая прямая запись в cursor — поле `+0x14`;
поэтому кандидат для проверки — сохранить это поле, выполнить тот же поиск B и
восстановить его. Вложенные catalog/cache функции могут менять собственные
флаги и кэш-страницы, так что статический разбор не доказывает безопасность
такого вызова.

Для готового track object есть штатная фабрика resource:
`FUN_1010b894` (`+0x10b894`). Для объекта, отличного от текущего
`player[0xa9]`, она создаёт 700-байтовый wrapper, получает метаданные из
`track+0x20`, вызывает `FUN_100de500` (`+0xde500`) с track id и затем связывает
wrapper со списком `player+1`. Открытие проходит через `FUN_100ec31c`
(`+0xec31c`) и создаёт отдельное состояние resource. Штатный caller передаёт
фабрике текущий `player[0xa9]` для восстановления A после ошибки переключения.
Передача B была бы новым поведением; общий
manager `DAT_100de660+8` и cache-service пока не проверены на одновременное
обслуживание A и B. Открывающий cache API `FUN_101f7d00` защищает операцию
своей блокировкой, а `FUN_101f7dc0` выделяет отдельную entry и добавляет её в
общее дерево. Это подтверждает несколько отдельных stream entries в cache,
но не одновременное декодирование A и B и не независимый player state. Поэтому
factory указывает на способ создать per-resource stream по track object, но не
доказывает безопасный второй playback.

Есть и lifecycle-ограничение: `FUN_100eb610` при обычной смене трека сначала
вызывает `FUN_100e1834`; с обычными флагами эта функция проходит по списку
resource-объектов player и вызывает `FUN_101018d8`, который удаляет каждый
объект из списка, закрывает его вложенный stream и освобождает память. Буквальный
флаг `0x20` в аргументе `FUN_100eb610` отключает именно этот обход списка.
Значит, заранее открытый B, добавленный фабрикой в список A, штатный handoff по
умолчанию уничтожит. Если патч удерживает активный player на A до конца
смешивания, B достаточно пережить только fade: после потребления последнего
PCM-блока обычный handoff может закрыть временный resource, штатно открыть B
заново и позиционировать его после уже прозвучавшей части. Это устраняет
обязательное требование передавать тот же resource через handoff, но требует
отложить commit штатного выбора трека до конца fade. Бесшовность повторного
открытия и точность позиции ещё нужно проверить. Флаг `0x20` здесь не требуется
и не объявляется безопасным. Режим
`0x20` используется штатным путём через `FUN_100ac148`, когда найденный в
списке wrapper имеет установленный byte `+0x2b8`; тот путь передаёт selector-у
флаг `8`, который затем превращается в `0x20` для handoff. Значение и смысл
этого wrapper-флага ещё не установлены, поэтому выставлять его для B наугад
нельзя. Factory `FUN_100a8180(700)` выделяет и обнуляет wrapper, а поиск
инструкций в функциях OSOS на immediate offset `0x2b8` нашёл
только чтения в `FUN_100ac148` и `FUN_100d19d0`, а сканер ADD-plus-store не
нашёл прямой записи по этому адресу. Setter флага пока не найден, поэтому
keep-resource ветку нельзя считать способом сохранить B; поле может задаваться
через ещё не разобранный косвенный путь либо ветка осталась неиспользуемой.

Следующий технический рубеж — безопасно получить B без выполнения
`FUN_100ac6f4`, открыть через `FUN_1010b894` отдельный resource и проследить
все последующие операции чтения/закрытия до file cache и provider. B нужно
держать до конца fade, после чего обычный handoff может открыть этот трек заново
и продолжить с позиции, уже прозвучавшей во время fade. Пока предварительный
resource B, его producer и смешивание PCM не реализованы.

Повторная проверка `FUN_1010b894` показала, что сама фабрика B-resource не
меняет `player+0xa9` и поля handoff `+0x9d9..+0x9e1`; эти записи делает caller
`FUN_100ac6f4` после её возврата. Фабрика создаёт wrapper для переданного track
object, открывает отдельный stream и добавляет wrapper в список `player+1`.
Поэтому открыть B на том же player до handoff выглядит реалистично. Однако
вызов полного MP3 item initializer-а `FUN_10127df4` дополнительно посылает
событие в общую `mp3dec_sync` очередь и обращается к service slot 5; эти общие
побочные эффекты должны быть отделены от инициализации второго decoder-а.

### Новый кандидат: поочерёдно сохранять и восстанавливать состояние provider-а

Сама загрузка provider-а 0 определяет две точные области, которые очищаются
при его инициализации:

* `0x40002514..0x40006124` — 15 376 байт с рабочими областями и состоянием;
* `0x40013aa8..0x40017694` — 15 340 байт с item-ом и вложенным MP3 context.

Суммарный снимок этих областей занимает 30 716 байт. Возможный вариант вместо
одновременного размещения двух копий decoder-а — сохранить B в heap, а при
последовательном запуске A и B копировать соответствующую страницу состояния
в фиксированные адреса IRAM, выполнять один decode job и сохранять её обратно.
Такой подход сохраняет абсолютные ссылки штатного overlay на IRAM, в том
числе рабочие области; для каждой дорожки отдельно нужно также хранить значения
указателей вывода `0x4000248c` и `0x40002510`. Ячейка активного item-а
`0x40013a64` может в обоих проходах указывать на текущий item по адресу
`0x40013aa8`.

Обработчик `FUN_101b1a10` (`OSOS+0x1b1a10`) читает активный item из
`0x40013a64`, передаёт в синтезатор контекст по `item+0x2000` и выбирает
рабочую область из `0x40002514` или `0x40004f24` вместе с одним из output-slot
указателей. Он также проверяет байт `item+0x260c`. Это подтверждает, что
active item и synthesis history входят в переключаемый путь. Значение второго
параметра callback-а и связь двух output slots с каналами/буферами ещё нужно
установить; подмена только active-item ячейки недостаточна.

Это инженерный вывод из известных границ очистки loader-а и адресов общего
вывода, а не подтверждённая способность прошивки переключать decoder-ы.
Вне этих областей остаются общая задача `0x149ee078`, service slot 5, файловый
cache и player/resource manager; их состояние копировать как часть provider-а
нельзя, а их повторный вход и порядок задач ещё не проверены. Также нужно
доказать, что весь закрытый callback использует только снимок IRAM и отдельный
file/resource item, измерить копирование и decode на временном бюджете, и
передать обе PCM очереди в микшер до I²S. Поэтому этот способ сужает
архитектурный вопрос до проверки сериализованного вызова, но не является
готовой реализацией второго потока.

Для времени запуска перехода есть точка-кандидат: `FUN_100ada0c` вызывает
`FUN_100abfb0(player, 0)`, а тот сравнивает поле времени `player+0x4b0` с
границей `player+0x9de`, добавляя константу `3000`. В этой ветке он ищет
кандидат через selector-вариант `FUN_10196a90` (`+0x196a90`), а затем может
передать найденный объект в `FUN_100ac6f4`. Другой путь `FUN_100ac4c4` вызывает
`FUN_101968c0`; оба selector-а сохраняют выбранный key при флаге `4`. Эта
ветка содержит 3 000-мс guard около границы трека, но пока не доказано, что это
именно запуск автоматического перехода: `FUN_100ada0c` также вызывается из
command-dispatch пути (`FUN_101b3138`, case 4) и playback-state observer-а
(`FUN_101e7a20`). Это точка-кандидат для захвата B до смены player; сначала
нужно различить причины вызова и подтвердить единицы времени. Простое изменение
константы до 10 000 без перехвата дальнейшей смены переключило бы player раньше,
чем завершится fade.

Поэтому рабочий control-flow кандидат — перехватить эту ветку до вызова
`FUN_100e1834` и selector/commit: при оставшемся времени `d` открыть/подготовить
B, запустить fade и вернуть управление, сохраняя A активным; после потребления
последнего fade-блока разрешить штатный commit. Константу guard-а можно заменить
значением `d` только вместе с этим перехватом. После commit новая B открывается
сначала штатно, затем кандидат `FUN_1010bb40` позиционирует её на уже прошедшее
время fade. Это ещё требует различить автоматический вызов от command/observer
вызовов, проверить шкалу времени и исключить повторный выбор B.

До создания кандидата для установки остаётся доказать и реализовать:

1. Независимые file/cache и decoder contexts для A и B без повторной настройки
   общего аудиовыхода; штатный commit нужно отложить до конца fade, после чего
   проверить повторное открытие B и позиционирование после handoff.
2. Независимый producer/PCM-ring второй дорожки и его синхронизацию с первым.
3. Runtime-аллокацию и освобождение RAM с безопасным отказом при нехватке места.
4. Wrapper в PCM callback и интеграцию экрана настройки в штатный Settings.
5. Проверку на физическом устройстве, включая обычное воспроизведение,
   переходы, паузу, смену трека и восстановление исходного раздела.

До выполнения этих пунктов ни расширенный контейнер, ни образ с вставленным
payload нельзя считать прошивкой с рабочим кроссфейдом.
